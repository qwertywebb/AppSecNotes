## 📌 **: CSRF (Cross-Site Request Forgery)**


### 1. Определение 

> **CSRF (Cross-Site Request Forgery)** — это уязвимость, при которой злоумышленник заставляет авторизованного пользователя выполнить нежелательное действие на сайте без его ведома. Атака использует существующую сессию пользователя (cookies, Basic Auth) и отправляет запрос от его имени.


### 2. Как работает CSRF

1. Пользователь авторизован на сайте (есть активная сессия).
2. Злоумышленник создаёт вредоносную страницу с формой или скриптом, который отправляет запрос на целевой сайт.
3. Пользователь переходит на страницу злоумышленника (или открывает письмо).
4. Браузер автоматически отправляет запрос с куками пользователя.
5. Сервер выполняет запрос, думая, что его отправил сам пользователь.


### 3. Отличие CSRF от XSS

| XSS | CSRF |
| :--- | :--- |
| Внедряет код на страницу | Заставляет выполнить действие |
| Крадёт данные (куки, сессии) | Выполняет действия от имени пользователя |
| Работает в браузере жертвы | Использует авторизацию жертвы |
| Цель — получение информации | Цель — изменение состояния (смена пароля, перевод денег) |


### 4. Условия для успешной атаки

- Пользователь авторизован на сайте.
- Сайт не проверяет источник запроса (Origin, Referer).
- В запросе нет CSRF-токена.
- Действие выполняется через GET или POST без дополнительной проверки.


### 5. Сценарий атаки (Пример)

1. Жертва авторизована в банке `bank.com`.
2. Злоумышленник отправляет письмо с ссылкой на вредоносную страницу.
3. На странице есть форма:
```html
<form action="https://bank.com/transfer" method="POST">
    <input type="hidden" name="to" value="attacker">
    <input type="hidden" name="amount" value="1000">
</form>
<script>document.forms[0].submit();</script>
```
4. Жертва открывает страницу → форма отправляется автоматически → деньги переведены.


### 6. Защита от CSRF (Что отвечать)

| Метод | Описание |
| :--- | :--- |
| **CSRF-токены** | Генерировать уникальный случайный токен для каждой формы/сессии и проверять его на сервере. |
| **SameSite Cookies** | Установить `SameSite=Lax` или `SameSite=Strict` для кук, чтобы они не отправлялись при кросс-доменных запросах. |
| **Проверка Origin / Referer** | Проверять, что запрос пришёл с того же домена. |
| **Re-authentication** | Запрашивать пароль перед критическими действиями (смена пароля, перевод денег). |
| **CAPTCHA** | Использовать капчу для чувствительных операций. |
| **Метод `POST` вместо `GET`** | Не использовать GET для изменяющих данных (но это не панацея). |


### 7. Пример защиты (CSRF-токен)

**На бэкенде (Python/Flask):**
```python
session['csrf_token'] = os.urandom(16).hex()
```

**На фронтенде (HTML):**
```html
<input type="hidden" name="csrf_token" value="{{ session.csrf_token }}">
```

**При отправке запроса:**
```python
if request.form['csrf_token'] != session['csrf_token']:
    abort(403)
```


### 8. Каверзные вопросы на собесе

**Q:** *«Может ли CSRF работать с JSON API?»*  
**A:** *«Да, если сайт принимает `application/json` и не проверяет Origin. Но часто CSRF в JSON сложнее, потому что браузер не отправляет `application/json` автоматически без `fetch` или `XMLHttpRequest`».*

**Q:** *«Что такое SameSite и как он помогает?»*  
**A:** *`SameSite=Lax` — куки отправляются только при переходе по ссылке (GET) с того же сайта. `Strict` — куки не отправляются вообще при кросс-доменных запросах. Это блокирует CSRF автоматически в современных браузерах».*

**Q:** *«Чем отличается CSRF от SSRF?»*  
**A:** *«CSRF — атака на пользователя (заставляет его выполнить запрос). SSRF — атака на сервер (заставляет сервер выполнить запрос куда угодно)».*


## 🎯 **Итог**

CSRF — опасная уязвимость, но её легко закрыть:
1. **CSRF-токен** — обязательный элемент для всех форм.
2. **SameSite** — современный стандарт, защищает автоматически.
3. **Проверка Referer/Origin** — дополнительный барьер.
