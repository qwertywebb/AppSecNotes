# OWASP Web Security Testing Guide (WSTG)

## Что такое WSTG

Когда начинаешь тестировать веб-приложение, возникает простой вопрос: **с чего начать?**

Допустим, есть интернет-магазин с:

* регистрацией пользователей;
* авторизацией;
* поиском товаров;
* корзиной;
* оплатой;
* отслеживанием заказов.

Можно начать с формы входа, затем перейти к поиску, потом к оплате. Но при таком подходе легко:

* несколько раз проверить одно и то же;
* забыть важную часть приложения;
* полностью пропустить определённый класс уязвимостей.

Для решения этой проблемы используется **OWASP Web Security Testing Guide (WSTG)**.

WSTG — это практическое руководство по тестированию безопасности веб-приложений. Оно содержит **более 90 отдельных тестов**, объединённых в 12 основных категорий.


# 12 категорий WSTG

WSTG охватывает практически всю поверхность атаки современного веб-приложения:

1. **Сбор информации**
2. **Конфигурация и управление развёртыванием**
3. **Управление идентификацией**
4. **Аутентификация**
5. **Авторизация**
6. **Управление сессиями**
7. **Проверка входных данных**
8. **Обработка ошибок**
9. **Криптография**
10. **Бизнес-логика**
11. **Клиентская часть**
12. **API**

Каждая категория содержит конкретные тесты с собственными идентификаторами.

Например:

```text
WSTG-INPV-01
```

— отдельный тест, связанный с отражённым XSS.

То есть WSTG — это не просто список «проверь XSS, SQLi и CSRF». Для каждого направления существуют конкретные процедуры проверки.


# Риск-ориентированный подход

WSTG предлагает не просто механически пройти весь список.

Основная идея — **приоритизировать тестирование исходя из риска**.

Приоритет определяется двумя основными факторами:

```text
Риск ≈ вероятность эксплуатации × потенциальный ущерб
```

Например, если в приложении есть API, через которое можно проводить платежи, его стоит исследовать раньше малозначимого функционала профиля пользователя.

Поэтому WSTG используется как **карта тестирования**, а не как обязательный список, который нужно проходить в любом порядке.


# WSTG и жизненный цикл разработки

Важная особенность WSTG заключается в том, что безопасность рассматривается **не только на этапе пентеста**.

Тестирование безопасности должно происходить на протяжении всего **SDLC — жизненного цикла разработки ПО**.

Выделяется пять основных фаз.


## Фаза 1 — до начала разработки

На этом этапе определяются требования безопасности.

Например, интернет-магазин **ShopSecure Inc.** обрабатывает платежи, поэтому заранее устанавливаются требования:

* соответствие PCI DSS;
* требования к защите платёжных данных;
* сроки устранения уязвимостей;
* допустимый уровень риска.

То есть безопасность определяется **до написания кода**.


## Фаза 2 — проектирование

До реализации приложения анализируется его архитектура.

Например, команда строит модель угроз для процесса оплаты и определяет, что API оформления заказа является критически важной частью системы.

Поэтому ещё на этапе проектирования предусматриваются:

* ограничение частоты запросов;
* проверка входных данных;
* корректная авторизация;
* защита платёжных операций.

Идея заключается в том, чтобы **заложить безопасность в архитектуру**, а не пытаться добавить её после разработки.


## Фаза 3 — разработка

Во время разработки проводится анализ исходного кода и отдельных компонентов.

Например, разработчики проверяют модуль восстановления пароля.

В результате обнаруживается проблема:

```text
токен восстановления пароля не имеет срока действия
```

Такую проблему можно обнаружить ещё до появления приложения в production.

WSTG в этом случае используется как ориентир для проверки конкретных механизмов, например аутентификации и восстановления доступа.


## Фаза 4 — развёртывание

После развёртывания необходимо проверить уже работающую систему.

Например:

* изменены ли стандартные credentials;
* корректно ли настроен TLS;
* отключены ли debug-функции;
* не доступны ли служебные endpoints;
* правильно ли настроены права доступа;
* не остались ли тестовые компоненты.

На этом этапе уже можно проводить полноценный penetration test.


## Фаза 5 — эксплуатация и сопровождение

Безопасность не заканчивается после запуска приложения.

После изменений необходимо повторно проверять соответствующие участки приложения.

Например, через три месяца ShopSecure добавляет новую систему рекомендаций товаров.

После этого повторно выполняются релевантные тесты WSTG, чтобы убедиться, что новая функциональность не создала:

* новые точки входа;
* проблемы с авторизацией;
* уязвимости в API;
* проблемы с обработкой пользовательского ввода.


# Преимущества WSTG

### 1. Полнота

Более 90 тестов позволяют системно покрывать различные части веб-приложения.

### 2. Практичность

WSTG содержит не только описание уязвимости, но и конкретные процедуры:

```text
что проверить
↓
как проверить
↓
какой результат ожидать
```

### 3. Структурированность

Тестер получает понятную структуру и меньше рискует забыть отдельный класс уязвимостей.

### 4. Актуальность

Руководство развивается сообществом специалистов по безопасности и адаптируется под современные архитектуры:

* SPA;
* REST API;
* микросервисы;
* современные веб-фреймворки.


# Недостатки

### 1. Полное прохождение занимает много времени

Если выполнять все тесты для каждого приложения, полноценный аудит может стать слишком дорогим по времени и ресурсам.

### 2. Некоторые тесты требуют специальных знаний

Например:

* криптографический анализ;
* сложное тестирование бизнес-логики;
* анализ архитектуры;
* специфические API.

### 3. Риск «чек-листового мышления»

Главная опасность — воспринимать WSTG как список:

```text
☑ SQL Injection
☑ XSS
☑ CSRF
☑ Authentication
☑ ...
```

и считать работу законченной.

Проблема в том, что реальная уязвимость может находиться **на стыке нескольких компонентов или бизнес-процессов** и не выглядеть как отдельный пункт чек-листа.

Поэтому опытный пентестер использует WSTG как **основу и структуру тестирования**, но не ограничивается им.


# Главное

**WSTG — это систематизированная методология тестирования веб-приложений.**

Её основная ценность не в том, что она говорит:

> «проверь XSS и SQL Injection».

А в том, что она помогает ответить на вопрос:

> **«Что именно мне нужно проверить в этом приложении, чтобы не пропустить важные области атаки?»**

При этом WSTG следует использовать **совместно с анализом конкретного приложения и оценкой риска**, а не механически выполнять все тесты подряд.
