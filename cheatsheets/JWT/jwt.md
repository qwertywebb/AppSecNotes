##  **JWT Security**

### 1. Определение 

**JWT (JSON Web Token)** — это компактный, самодостаточный способ передачи информации между сторонами в виде JSON-объекта. Он состоит из трёх частей: Header, Payload, Signature. JWT часто используется для аутентификации и авторизации. Однако его неправильное использование может привести к серьёзным уязвимостям: подделка токенов, кража сессий и доступ к чужим данным.

| Часть | Описание |

| **Payload** | Данные (claims): `sub`, `name`, `iat`, `exp`, `role`. |
| **Signature** | Подпись, созданная с использованием секрета или приватного ключа. |


### 3. Основные уязвимости JWT

| Уязвимость | Описание | Пример |
| :--- | :--- | :--- |
| **Алгоритм `none`** | Подпись не проверяется, если указан `alg: none`. | `{"alg": "none", "typ": "JWT"}` |
| **Атака смешения алгоритмов** | Смена `RS256` на `HS256` при использовании публичного ключа как секрета. | Использовать публичный ключ как HMAC-секрет. |
| **Слабый секрет** | Секрет можно подобрать через брутфорс (hashcat, john). | `secret`, `password`, `123456`. |
| **Утечка секрета** | Секрет хранится в коде или `.env`, доступен злоумышленнику. | `JWT_SECRET = "supersecret"` |
| **Кража токена** | Перехват токена через XSS, MITM, открытые логи. | `document.cookie` (если нет `HttpOnly`). |
| **Отсутствие проверки `exp`** | Токен живёт вечно, даже если истёк. | `"exp": 0` или нет поля `exp`. |
| **Слабый механизм обновления** | Refresh token не защищён или не отзывается. | Бесконечная сессия. |


### 4. Атака: Алгоритм `none`

**Header:**
```json
{
  "alg": "none",
  "typ": "JWT"
}
```

**Payload:**
```json
{
  "sub": "admin",
  "role": "admin"
}
```

**Результат:** Подпись не проверяется, токен считается валидным.

**Защита:**
```python
# Проверка, что alg не равен none
if header['alg'] == 'none':
    raise Exception('Invalid algorithm')
```


### 5. Атака: Смешение алгоритмов (HS256 vs RS256)

**Как работает:**
1. Сервер ожидает `RS256` (асимметричный).
2. Злоумышленник меняет `alg` на `HS256`.
3. Сервер использует публичный ключ как HMAC-секрет.
4. Злоумышленник подписывает токен публичным ключом.
5. Сервер проверяет и принимает поддельный токен.

**Защита:**
```python
# Чётко указывать алгоритм при верификации
jwt.decode(token, public_key, algorithms=['RS256'])
```


### 6. Атака: Слабый секрет

**Брутфорс через hashcat:**

### 7. Хранение и передача JWT

| ❌ Плохо | ✅ Хорошо |
| :--- | :--- |
| Хранить в `localStorage` | Хранить в `HttpOnly`, `Secure`, `SameSite` cookie |
| Передавать в URL | Передавать в `Authorization: Bearer` |
| Не шифровать | Использовать `JWE` (JSON Web Encryption) |
| Долгий TTL (несколько дней) | Короткий TTL (15–60 минут) |


### 8. Защита от JWT-атак 

| Защита | Описание |
| :--- | :--- |
| **Использовать `RS256` вместо `HS256`** | Асимметричный алгоритм безопаснее для распределённых систем. |
| **Проверять `alg`** | Запретить `none` и недопустимые алгоритмы. |
| **Сложный секрет** | Длина > 32 символов, использовать `secrets` или `openssl`. |
| **Короткий TTL** | Access token живёт 15–60 минут. |
| **Отзыв токенов (Revocation)** | Хранить blacklist в Redis. |
| **Использовать `HttpOnly` и `Secure`** | Защита от XSS и MITM. |
| **Использовать `Refresh Token`** | Для обновления access token без повторного ввода пароля. |
| **Проверка `exp`** | Всегда проверять срок действия токена. |


### 9. Пример безопасного использования JWT (Python)

```python
import jwt
import secrets
from datetime import datetime, timedelta

SECRET = secrets.token_urlsafe(32)

def create_token(user_id, role):
    payload = {
        'sub': user_id,
        'role': role,
        'iat': datetime.utcnow(),
        'exp': datetime.utcnow() + timedelta(minutes=15)
    }
    return jwt.encode(payload, SECRET, algorithm='HS256')

def verify_token(token):
    try:
        payload = jwt.decode(token, SECRET, algorithms=['HS256'])
        return payload
    except jwt.ExpiredSignatureError:
        return {'error': 'Token expired'}
    except jwt.InvalidTokenError:
        return {'error': 'Invalid token'}
```


### 10. Каверзные вопросы 

**Q:** *«Чем отличается HS256 от RS256?»*  
**A:** *«HS256 — симметричный (один секрет). RS256 — асимметричный (приватный и публичный ключ)».*

**Q:** *«Как защититься от атаки смешения алгоритмов?»*  
**A:** *«Указывать явный алгоритм при верификации: `algorithms=['RS256']`».*

**Q:** *«Можно ли хранить JWT в `localStorage`?»*  
**A:** *«Не рекомендуется. Лучше использовать `HttpOnly` cookie».*

**Q:** *«Что такое Refresh Token?»*  
**A:** *«Токен для обновления Access Token без повторной аутентификации. Живёт дольше (часы/дни) и хранится в безопасном месте».*


## 🎯 **Итог**

JWT — мощный инструмент, но требует правильной настройки.

Главные риски:
1. **Алгоритм `none`** → подделка токена.
2. **Смешение алгоритмов** → подделка через публичный ключ.
3. **Слабый секрет** → брутфорс.
4. **Кража токена** → XSS, MITM.

Защита:
1. **Сложный секрет.**
2. **Короткий TTL (15–60 минут).**
3. **Проверка `alg`.**
4. **Хранение в `HttpOnly` cookie.**
5. **Использование Refresh Token.**
