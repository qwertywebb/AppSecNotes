# Шифрование и подпись в JWT

**Шифрование** — это процесс преобразования информации в неразборчивый формат, который может быть прочитан только с помощью специального ключа или пароля. Если ключ не нужен, то этот механизм небезопасен.

Процесс шифрования делит исходное сообщение на блоки определенного размера (например, в AES это 16 байт) и применяет математические операции к каждому блоку.

**Симметричное шифрование** использует один и тот же ключ для шифрования и дешифрования данных. Это означает, что обе стороны должны иметь доступ к этому ключу, что может быть проблемой при передаче ключа по незащищенным каналам.


## JWT: Подпись, а не шифрование

**Важный нюанс:** JWT по умолчанию **не шифрует** данные (payload). Он их **подписывает**, чтобы гарантировать, что данные не были изменены. Содержимое JWT (header + payload) просто кодируется в Base64, и любой может его прочитать. Поэтому никогда не кладите в JWT пароли или секреты!


## HS256 (Симметричная подпись)

- **Как работает:** Используется **один секретный ключ**, который знают и сервер-выдающий (Issuer), и сервер-проверяющий (Audience). Они оба используют этот ключ для создания и проверки подписи.
- **Где применяется:** В монолитных системах или микросервисах, где все сервисы находятся в одной доверенной зоне и могут разделять один секрет. 
- **Безопасность:** Ключ должен быть сложным и надежно храниться (в `Secrets Manager`, а не в коде!). Если ключ скомпрометирован, злоумышленник сможет подделывать любые токены.


## RS256 (Асимметричная подпись)

- **Как работает:** Используется **пара ключей**: приватный (секретный) ключ для **подписи** токенов и публичный (открытый) ключ для **проверки** подписи.
- **Где применяется:** В распределенных системах (например, микросервисная архитектура с SSO). **Авторизационный сервер (IdP)** подписывает токены приватным ключом. Сотни других сервисов получают публичный ключ (можно даже из кеша через `.well-known/jwks.json`) и проверяют токен **без доступа к приватному ключу**.
- **Безопасность:** Это безопаснее для инфраструктуры, потому что приватный ключ знает только один сервис. Даже если один микросервис взломают, злоумышленник не получит доступ к подписи всех токенов.


## Запомнить для собеса:

| **HS256** | Один общий секрет | Простые системы, один сервер |
| **RS256** | Пара ключей (приватный + публичный) | Микросервисы, SSO, сторонние приложения |


## Важно про атаки на JWT:

1. **Алгоритм `none`** — если разработчик забыл проверять `alg`, злоумышленник может изменить заголовок на `"alg": "none"` и удалить подпись. Библиотека воспримет это как валидный токен без проверки.
2. **Key Confusion Attack** — если бэкенд ожидает RS256, но получает HS256, он попытается проверить подпись публичным ключом, используя его как симметричный секрет, что может привести к компрометации.
