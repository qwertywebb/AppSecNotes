# 🔐 PENTESTER CHEATSHEET: OAuth 2.0 & 1.0a

## 📌 ЧТО ТАКОЕ OAuth?

**OAuth** (Open Authorization) — это **открытый протокол авторизации**, который позволяет сторонним приложениям (клиентам) получать **ограниченный доступ** к ресурсам пользователя на сервере (например, к его данным в Google, Facebook, GitHub) **без передачи логина и пароля**.

Простыми словами: OAuth — это технология, с помощью которой вы можете войти на сайт, используя аккаунт Google или VK, не вводя на этом сайте свои пароли от Google/VK. Вместо этого вы даёте сайту **токен** — временный "ключ" с определёнными правами.

### КЛЮЧЕВЫЕ ПОНЯТИЯ:
- **Resource Owner** (владелец ресурса) — пользователь, который владеет данными.
- **Client** (клиент) — стороннее приложение, которое хочет получить доступ к данным пользователя.
- **Authorization Server** (сервер авторизации) — выдаёт токены доступа после успешной аутентификации пользователя.
- **Resource Server** (сервер ресурсов) — хранит данные пользователя и принимает запросы с токенами доступа.
- **Access Token** — ключ доступа, который клиент предъявляет для получения данных.
- **Refresh Token** — (опционально) долгоживущий токен для получения нового Access Token без участия пользователя.

**Важно**: OAuth решает задачу **авторизации** (что можно делать), а не **аутентификации** (кто ты). Однако OpenID Connect (надстройка над OAuth 2.0) добавляет и аутентификацию.


## 📚 ТЕОРЕТИЧЕСКАЯ БАЗА

### OAuth 1.0a (RFC 5849)
**Архитектура**: "Подпись всего" (cryptographic signing)
- **Основная идея**: Клиент подписывает каждый запрос с помощью HMAC-SHA1 или RSA-SHA1, используя секретные ключи (consumer secret + token secret)
- **Поток**:
  1. **Request Token** (временный) → `/oauth/request_token`
  2. **User Authorization** → перенаправление пользователя
  3. **Access Token** → обмен Request Token на Access Token
  4. **Подпись каждого API-запроса** (OAuth signature)
- **Безопасность**: Не требует TLS (так как подпись защищает от подмены), но всё равно рекомендуется HTTPS
- **Сложность**: Громоздкая генерация подписей (nonce, timestamp, параметры сортируются, конкатенируются, подписываются)
- **Сейчас**: Практически вытеснен OAuth 2.0, но встречается в legacy-системах (Twitter API v1, некоторые корпоративные решения)

### OAuth 2.0 (RFC 6749)
**Архитектура**: "Доверяй TLS" (bearer tokens)
- **Основная идея**: Клиент получает токен доступа (access token), который предъявляет в заголовке `Authorization: Bearer <token>`
- **Потоки (Grants)**:
  - **Authorization Code** (самый безопасный, для серверных приложений)
  - **Implicit** (устарел, для SPA) — токен возвращается в URL
  - **Resource Owner Password Credentials** (только для доверенных клиентов)
  - **Client Credentials** (сервер-сервер, без пользователя)
- **Безопасность**: Полностью полагается на TLS для защиты токенов во время передачи
- **Плюсы**: Проще реализация, гибкость
- **Минусы**: Если TLS скомпрометирован — все токены уязвимы
- **Доп. механизмы**: PKCE (RFC 7636) — защита публичных клиентов от перехвата кода


### КЛЮЧЕВЫЕ ОТЛИЧИЯ

| Аспект | OAuth 1.0a | OAuth 2.0 |
|--------|------------|-----------|
| **Транспорт** | Не требует TLS (подпись) | **Требует TLS** (обязательно) |
| **Подпись** | Каждый запрос подписывается | Bearer token в заголовке |
| **Сложность** | Высокая (генерация signature) | Низкая |
| **Токены** | Request Token → Access Token | Authorization Code → Access Token |
| **Срок жизни** | Обычно долгие | Короткие access + refresh token |
| **Популярность** | Legacy | Стандарт де-факто |
| **CSRF-защита** | Не требуется (подпись) | **Обязателен параметр state** |
| **PKCE** | Не применим | Для публичных клиентов |
| **Уязвимости** | Подпись можно подделать (слабые nonce) | Перехват токенов, CSRF, redirect_uri |


## 🎯 OAuth 2.0 — АТАКИ И ТЕСТИРОВАНИЕ

### 1. REDIRECT_URI — ГЛАВНАЯ БОЛЬ (90% багов)

**Суть**: Сервер авторизации должен вернуть код строго на заранее зарегистрированный URI. Кривая валидация = перехват кода.

#### 🔍 ЧТО ПРОБОВАТЬ (матрица атак):

| № | Вектор | Пример | Вероятность | Профит |
|---|--------|--------|-------------|--------|
| 1 | **Полная замена домена** | `/?redirect_uri=https://evil.com/callback` | Средняя (если не строгая валидация) | ⭐⭐⭐⭐⭐ |
| 2 | **Open Redirect внутри домена** | `/?redirect_uri=https://legit.com/redirect?url=https://evil.com` | Высокая [citation:2][citation:8] | ⭐⭐⭐⭐⭐ |
| 3 | **Subdomain Takeover** | `/?redirect_uri=https://dead-subdomain.legit.com` | Низкая (нужен мертвый поддомен) | ⭐⭐⭐⭐ |
| 4 | **Path Traversal** | `/?redirect_uri=https://legit.com/callback/../../../evil.com` | Низкая | ⭐⭐⭐ |
| 5 | **Fragment в URI** | `/?redirect_uri=https://legit.com/callback#` | Средняя (JS может прочитать фрагмент) [citation:3][citation:8] | ⭐⭐⭐⭐ |
| 6 | **Разные схемы** | `/?redirect_uri=http://legit.com` (если сайт требует HTTPS) | Низкая | ⭐⭐⭐ |
| 7 | **Двойной редирект** | `/?redirect_uri=https://legit.com//redirect?url=//evil.com` | Средняя (обход валидации) | ⭐⭐⭐⭐ |

#### 🛡️ ОБХОД ВАЛИДАЦИИ (если редирект заблокирован):
- **Проверка по префиксу**: `*.legit.com` → `xss.legit.com` (если есть XSS на поддомене — лутаем код) [citation:3]
- **Проверка по суффиксу**: `legit.com` → `legit.com.evil.com` (если валидация тупая)
- **Exact match**: Ищи открытый редирект на том же домене в другом месте (например, `/logout?continue=attacker.com`) [citation:2]


### 2. STATE — ЗАЩИТА ОТ CSRF (или её отсутствие)

**Суть**: Если параметр `state` отсутствует или предсказуем — можно привязать свой аккаунт к жертве.

#### 🔄 АТАКА (OAuth CSRF → Account Takeover):
```
1. Злоумышленник логинится через OAuth, перехватывает Authorization Code (код)
2. Создаёт страницу с iframe, отправляющим этот код на callback жертвы:
   <iframe src="https://victim.com/callback?code=ЗЛОЙ_КОД&state=ПРЕДСКАЗУЕМЫЙ"></iframe>
3. Если state не проверяется → код привязывается к аккаунту жертвы
4. Злоумышленник заходит через свой аккаунт, который теперь привязан к жертве
```
[citation:2]

#### ✅ ЧТО ПРОВЕРЯТЬ:
- [ ] **Отсутствие** параметра `state` в запросе
- [ ] **Статичный** state (`123`, `test`, `state`)
- [ ] **Предсказуемый** state (инкремент, timestamp, MD5(email), слабая рандомизация) [citation:7]
- [ ] **Не проверяется** при возврате (можно подставить любой)


### 3. CSRF + ACCOUNT TAKEOVER (без перехвата кода)

**Сценарий**: Жертва авторизована на сайте, мы заставляем её браузер выполнить OAuth flow с нашим аккаунтом.

**Результат**: Наш аккаунт привязывается к жертве (если это функция "Connect") → мы заходим через него.

**Важно**: Атака работает, если привязка не требует подтверждения паролем и просто берёт код. [citation:2]


### 4. TOKEN LEAKAGE (где могут утечь токены)

| Место | Описание | Риск |
|-------|----------|------|
| **Referer Header** | Редирект на внешний ресурс после логина | ⭐⭐⭐⭐ |
| **Логи сервера** | Токены в URL (особенно при GET-запросах) | ⭐⭐⭐⭐⭐ |
| **Browser History** | Implicit Flow (токен в URL) → остаётся в истории | ⭐⭐⭐⭐ [citation:10] |
| **HTTP (без TLS)** | Сниффинг в публичных сетях | ⭐⭐⭐⭐⭐ |
| **localStorage** | XSS → доступ к токену [citation:5] | ⭐⭐⭐⭐⭐ |
| **sessionStorage** | XSS → доступ к токену [citation:5] | ⭐⭐⭐⭐ |
| **HttpOnly Cookie** | Без флага Secure → сниффинг; без HttpOnly → XSS | ⭐⭐⭐ |


### 5. PKCE — ЗАЩИТА ОТ ПЕРЕХВАТА КОДА

**Суть**: PKCE (Proof Key for Code Exchange) добавляет `code_challenge` (S256) и `code_verifier`.

#### 🔓 БЕЗ PKCE:
- Если перехватили `authorization code` (через redirect_uri) → можно обменять на токен [citation:5]

#### 🛡️ С PKCE:
- Даже с кодом нужен `code_verifier` → без него токен не получить

#### ✅ ЧТО ПРОВЕРЯТЬ:
- [ ] Есть ли `code_challenge` в запросе авторизации?
- [ ] Если нет → код можно использовать повторно (replay)


### 6. TOKEN VALIDATION НА РЕСУРСЕ (API)

**Даже если украли токен, API может его не принять, если проверяет:**

| Параметр | Проверка | Последствия |
|----------|----------|-------------|
| **aud** (audience) | Должен совпадать с API | Если не проверяется → токен от одного API работает для другого [citation:5] |
| **iss** (issuer) | Должен быть правильный сервер | Если не проверяется → можно подставить чужой токен |
| **exp** (expiration) | Если токен вечный → подарок | Если истек → replay не работает |
| **sub** (subject) | Привязка к пользователю | Если не привязан → доступ к чужим данным |
| **scope** | Ограничение прав | Если слишком широкий → PII leakage [citation:6] |


### 7. SCOPES (права доступа)

#### ✅ ЧТО ПРОВЕРЯТЬ:
- [ ] Запрашивает ли клиент **лишние** скоупы? (например, доступ к почте, когда нужен только логин) [citation:5]
- [ ] Можно ли **расширить** права? (если нет подписи запроса)
- [ ] Что будет, если скоуп **слишком широкий**? (PII leakage) [citation:6]


## 🧪 МАНУАЛЬНОЕ ТЕСТИРОВАНИЕ

### ШАГ 1: Перехват Authorization Request
```
GET /authorize?
    response_type=code
    client_id=...          <- Идентификатор клиента
    redirect_uri=...       <- КРИТИЧНО! Меняем здесь
    scope=...              <- Проверяем можно ли расширить
    state=...              <- Проверяем случайность
    code_challenge=...     <- PKCE защита? (S256)
```

### ШАГ 2: Перехват Token Exchange
```
POST /token
    grant_type=authorization_code
    code=...               <- Пробуем replay
    redirect_uri=...
    client_id=...
    code_verifier=...      <- Если есть PKCE
```

### ШАГ 3: Проверка API
```
GET /api/user
    Authorization: Bearer <украденный_токен>
```


## 🚀 АВТОМАТИЗИРОВАННЫЕ ИНСТРУМЕНТЫ

- **Burp Suite**: Repeater, Intruder (fuzz redirect_uri)
- **Nuclei**: Templates for OAuth misconfigurations
- **oauth-fuzzer**: Специализированный фуззер
- **Custom scripts**: Перебор state, редиректов


## 📋 ЧЕКЛИСТ ПЕНТЕСТЕРА (QUICK CHECKLIST)

- [ ] Есть ли открытый редирект на том же домене, куда можно завернуть?
- [ ] Есть ли параметр `state`? Он рандомный? [citation:7]
- [ ] Есть ли PKCE (`code_challenge`)? [citation:5]
- [ ] Работает ли код дважды? (replay)
- [ ] Токены передаются в URL? (Implicit Flow — deprecated, но бывает)
- [ ] Куда сохраняются токены на клиенте? (localStorage = instant XSS vector) [citation:5]
- [ ] Валидируется ли `aud` (audience) на API? [citation:5]
- [ ] Можно ли расширить `scope`?
- [ ] Не записываются ли токены в логи? (особенно GET-запросы)


## 🔥 ВАЖНЫЕ ВЫВОДЫ

### Критические точки:
- **redirect_uri** = святая святых. Любая неточность валидации = Account Takeover [citation:2]
- **state** = должен быть рандомным и проверяться. Без него — CSRF и привязка чужого аккаунта [citation:7]
- **PKCE** = обязателен для публичных клиентов. Без него — код можно обменять, если перехватили [citation:5]
- **Токены** = хранить в HttpOnly, не в localStorage. XSS — и всё пропало [citation:5]
- **Scope** = минимально необходимые права. Иначе PII leakage [citation:6]

### Всегда проверять:
- [ ] Что будет, если authorization code использовать дважды?
- [ ] Что будет, если вставить свой код в чужой flow (если нет state)?
- [ ] Поддерживается ли обмен кода через POST с redirect_uri, отличным от исходного?
