## Цель

Получить доступ к функционалу приложения, проанализировать бизнес-логику начисления вознаграждений и получить флаг путем эксплуатации логической уязвимости.

# 2. Исследование веб-приложения

На 3000 порту были доступны две страницы:

* регистрация;
* авторизация.

Была зарегистрирована тестовая учетная запись:

```
test:testtest
```

После успешной авторизации произошло перенаправление на страницу:

```
/dashboard
```

На панели управления присутствовала возможность получения ежедневной награды посредством выполнения запроса:

```
POST /claim
```

Каждый успешный запрос увеличивал баланс пользователя на **50 Ponzi**.

Также приложение информировало, что после достижения баланса **150 Ponzi** пользователю будет доступна эксклюзивная награда.

После повторной попытки получения бонуса сервер возвращал ограничение:

```http
HTTP/1.1 429 Too Many Requests

{
    "error":"Reward already claimed. Please wait before claiming again.",
    "secondsRemaining":86297
}
```

Из этого был сделан вывод, что разработчики реализовали ограничение на получение награды не чаще одного раза в сутки.


# 3. Поиск альтернативных способов получения награды

Поскольку ожидание нескольких суток противоречило логике прохождения лабораторной работы, было сделано предположение, что ограничение можно обойти путем поиска уязвимости в реализации API.

Для начала был выполнен фаззинг директорий и эндпоинтов.

Были обнаружены следующие ресурсы:

```

```

Эндпоинт `/vault` был недоступен из-за отсутствия необходимых привилегий.

Дополнительных административных маршрутов обнаружено не было.

# 4. Эксплуатация Race Condition

Следующим этапом было принято решение проверить приложение на наличие **Race Condition (состояние гонки)**.

Логика предполагала следующее:

* клиент отправляет запрос;
* сервер проверяет, получал ли пользователь награду сегодня;
* если проверка успешна — начисляет 50 Ponzi;
* после начисления обновляет информацию о времени последнего получения награды.

Если несколько запросов попадут на сервер практически одновременно, существует вероятность, что каждый поток выполнит проверку до того, как другой поток успеет обновить состояние пользователя.

Для проверки данной гипотезы использовался **Burp Suite Repeater**.

Последовательность действий:

1. Перехватить запрос `POST /claim`.
2. Передать его в **Repeater**.
3. Создать группу запросов.
4. Продублировать вкладку с одинаковым запросом несколько раз.
5. В настройках группы выбрать:

```
Send group in parallel
```

6. Одновременно отправить все запросы.

Эксплуатация оказалась успешной.

Несколько запросов одновременно прошли проверку ограничения и каждый из них начислил награду.

В результате баланс увеличился значительно выше предусмотренного бизнес-логикой значения.

Финальный ответ приложения:

```http
HTTP/1.1 200 OK

{
    "message":"Staking reward claimed successfully.",
    "reward":50,
    "newBalance":500,
    "tier":"Whale",
    "priceSnapshot":4.2
}
```

После достижения необходимого количества Ponzi был успешно получен флаг.

---

# Почему это сработало

Причиной успешной эксплуатации стала классическая уязвимость **Race Condition** (CWE-362 — Concurrent Execution using Shared Resource with Improper Synchronization).

Приложение выполняло операции в следующем порядке:

```
Проверить возможность получения награды
        ↓
Начислить 50 Ponzi
        ↓
Записать информацию о том, что награда уже получена
```

Когда несколько идентичных запросов поступили одновременно, каждый обработчик увидел, что награда еще не была получена, поскольку другой поток еще не успел обновить состояние пользователя.

В результате каждый параллельный запрос независимо начислил вознаграждение.

Таким образом ограничение «один раз в сутки» было полностью обойдено.

Подобная ошибка называется **TOCTOU (Time Of Check — Time Of Use)** — состояние, при котором между моментом проверки условия и моментом изменения состояния проходит время, достаточное для возникновения гонки.

---

# Название уязвимости

Эксплуатация основана на следующих типах уязвимостей:

* Race Condition;
* TOCTOU (Time Of Check Time Of Use);
* Business Logic Vulnerability;
* Improper Synchronization (CWE-362).

# Возможные последствия

В реальном приложении подобная ошибка могла бы привести к:

* многократному начислению денежных средств;
* повторному получению бонусов;
* повторной выплате кэшбэка;
* бесконечному начислению игровой валюты;
* обходу лимитов на получение вознаграждений;
* финансовым потерям компании.

Для криптовалютных сервисов подобная ошибка способна привести к многократному выводу средств и полной компрометации финансовой модели приложения.

# Как избежать подобной уязвимости

Для предотвращения подобных атак необходимо обеспечить атомарность операции начисления награды.

Наиболее распространенные способы защиты:

Можно оформить рекомендации так, чтобы они были понятны не только безопаснику, но и разработчику.

---

### Рекомендации по устранению уязвимости

Для предотвращения атак типа **Race Condition** необходимо исключить ситуацию, при которой несколько запросов одновременно проходят проверку и изменяют состояние приложения.

Наиболее распространенные способы защиты:

* **Выполнять проверку и обновление данных в рамках одной транзакции базы данных.**
  Проверка условий (например, что награда еще не получена) и последующее обновление данных должны выполняться как одна неделимая операция. Пока транзакция не завершится, другие запросы не должны иметь возможность изменить те же данные.

* **Использовать блокировки строк (Row Locking, `SELECT ... FOR UPDATE`).**
  При работе с реляционными СУБД необходимо блокировать запись пользователя на время обработки запроса. Пока один процесс изменяет данные, остальные запросы будут ожидать завершения операции, а не выполнять проверку параллельно.

* **Применять атомарные операции обновления.**
  Вместо логики вида:

  ```
  if (!claimedToday) {
      claimedToday = true;
      balance += 50;
  }
  ```

  необходимо выполнять одно атомарное обновление на уровне базы данных, например:

  ```
  UPDATE users
  SET balance = balance + 50,
      claimedToday = true
  WHERE id = ?
    AND claimedToday = false;
  ```

  или в MongoDB:

  ```
  findOneAndUpdate(
      { _id: id, claimedToday: false },
      { $set: { claimedToday: true }, $inc: { balance: 50 } }
  )
  ```

  В этом случае база данных самостоятельно гарантирует, что только **один** запрос сможет изменить запись. Все последующие запросы увидят, что условие уже не выполняется.

* **Использовать распределенные блокировки (Redis Lock, Mutex).**
  Если приложение работает на нескольких серверах, одного механизма блокировок внутри процесса недостаточно. Перед выполнением критической операции следует получить распределенную блокировку (например, через Redis), чтобы одновременно обработкой конкретного пользователя занимался только один экземпляр приложения.

* **Повторно проверять состояние непосредственно перед записью результата.**
  Даже если предварительная проверка уже была выполнена, перед сохранением изменений необходимо убедиться, что данные не изменились другим запросом за время обработки.

* **Реализовать механизм идемпотентности (Idempotency Keys).**
  Каждому запросу на выполнение операции присваивается уникальный идентификатор. Если клиент повторно отправит тот же запрос (случайно или намеренно), сервер распознает его как уже обработанный и не выполнит начисление повторно.

# Обнаруженные уязвимости

* Race Condition (CWE-362);
* TOCTOU (Time Of Check Time Of Use);
* Business Logic Vulnerability;
* Improper Synchronization.

# Итог

В ходе исследования веб-приложения было установлено, что механизм ежедневного начисления вознаграждения реализован без необходимой синхронизации между конкурентными запросами. Используя возможность параллельной отправки нескольких идентичных HTTP-запросов через Burp Suite Repeater, удалось одновременно пройти проверку ограничения «один раз в сутки» и многократно начислить вознаграждение. Эксплуатация классической уязвимости Race Condition позволила увеличить баланс пользователя до 500 Ponzi, получить статус **Whale** и успешно извлечь флаг без ожидания истечения установленного разработчиками временного интервала.
